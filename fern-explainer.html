Fern

Postman עוזר לבנות API טוב. Fern עוזר לגרום לו להיות בשימוש בפועל — על ידי מפתחים וגם על ידי AI Agents.

⠿

Postman עוזר לך לבנות, לבדוק ולנהל API. 

Fern לוקח את אותו API ועושה לו משהו אחר לגמרי — הוא הופך אותו לקל לצריכה, גם על ידי מפתחים וגם על ידי AI Agents.

ה-API של הלקוח יכול להיות מצוין מבחינה טכנית, אבל ברגע שמפתח חיצוני או פנימי צריך להשתמש בו, הוא שואל שאלות פשוטות: איפה ה-API? איך אני מתחבר? איזה SDK יש בשפה שלי? האם התיעוד בכלל מעודכן?

  Fern יושב בדיוק בנקודה הזו — בצד ה-Consumption, לא ה-Governance. הוא לוקח את ה-API Specification ובונה סביבו אוטומטית תיעוד, SDKs, כלי שורת פקודה, ושרתי MCP ל-AI Agents.

התיעוד מוגש בצד השרת בפורמט Markdown (ולא בצד ה-Client), כך ש-Claude Code, Codex ו-Cursor יכולים לקרוא אותו ולעבוד איתו ישירות. ה-SDK חשוב בפרט לסוכני AI - סוכן שבונה מול API בלי SDK מקבל החלטות לא עקביות בנושאי Auth ו-Pagination — מה שמעלה את צריכת ה-Token ומאריך את זמן הפיתוח

מכאן אתה עובר לבעיה

נניח שחברה בנתה API. מבחינת צוות הפיתוח — הוא קיים, הוא עובד, הכל בסדר. אבל מפתח חיצוני שמגיע מבחוץ שואל שאלות אחרות לגמרי: איפה ה-API, איך עושים Authentication, איזה Endpoint רלוונטי, איך מטפלים ב-Pagination, איזה SDK צריך, ואיפה בכלל הדוגמאות. וככל שה-API משתנה — וזה טוב, זה סימן שהעסק חי — נוצרת בעיה נוספת: השכבות API → Documentation → SDK → Examples יוצאות מסנכרון אחת מהשנייה. זה Drift, וזה הכאב המרכזי שרוב הארגונים חווים בלי לשים לו שם.

הלקוח לא באמת קונה Documentation. הוא קונה דרך להפוך APIs למוצר שקל יותר לצרוך. ה-Documentation הוא בדרך כלל נקודת הכניסה, אבל Fern נותן סביב אותו API הרבה יותר מזה — וזה מה שהופך אותו לרחב בהרבה מכלי Documentation בלבד.

שאלות Discovery — כולל השאלה שהיא כסף
⠿
תרחיש ראשון שאתה יכול לפרוש: חברת ביטוח
חברת ביטוח גדולה

יש לה APIs עבור לקוחות, פוליסות, תביעות, הצעות מחיר וסוכנים — והיא מאפשרת לשותפים ולסוכנויות ביטוח להתחבר אליהם. המצב: מאות APIs, תיעוד במקומות שונים, SDKs שנבנים ידנית, וכל שינוי ב-API דורש לעדכן כמה מקומות.

הבעיה העסקית: סוכנות חדשה רוצה להתחבר. היא צריכה לעבור תיעוד → להבין Authentication → להבין Endpoints → לבנות אינטגרציה → לפתור בעיות. Fern יכול לתת: API Specification → Documentation + SDKs + Examples — וה-Key מקבל דרך הרבה יותר מסודרת להתחיל לעבוד.

ובגלל שמדובר בחברת ביטוח, היכולת של Fern לרוץ Self-Hosted (להריץ את יצירת ה-Documentation וה-SDKs בתוך התשתית של הלקוח, כולל On-Prem או Private Cloud) יכולה להיות חלק משמעותי מהשיחה — שווה להעלות את זה מוקדם, לא לחכות שישאלו. זה רלוונטי בעיקר לתעשיות מוסדרות — בנקאות, ביטוח, תשלומים, ביטחוני (חברות כמו Bloomberg, Anduril ו-Intuit עובדות ב-Self-Hosted). נקודה שכדאי לזכור: בפועל, הרבה מהלקוחות האלה עוברים ל-Hosted בהמשך, לאחר שהם רואים בעצמם את ה-Compliance וה-Performance של הסביבה המנוהלת — אז אפשר להתחיל Self-Hosted בלי חשש, ולתת לזה להתפתח.

למי לפנות בחברת ביטוח כזו: Head of Open Banking/API או Head of API Product (ה-Lead), Head of Developer Portal (תפקיד שני). CISO/Compliance נכנס לתמונה כשעולה Audit רגולטורי (DORA/PSD3) — זה בדיוק הרגע שבו Self-Hosted עובר משאלה תיאורטית לדרישה.

שאלת Discovery לסגירת התרחיש "כמה זמן לוקח היום לשותף חדש לעבור מהשלב שבו הוא מקבל גישה ל-API עד שהאינטגרציה הראשונה שלו עובדת?"
⠿
תרחיש שני: חברת אשראי / תשלומים
חברת אשראי שמאפשרת לבתי עסק להתחבר ל-Payment APIs

יש לה: Payment API, Refund API, Customer API, Transaction API, Fraud API, ו-Webhooks — והיא רוצה ש-Partners ו-Developers יתחברו במהירות.

הבעיה: ה-API משתנה לעיתים קרובות. כל שינוי דורש לעדכן Docs + SDK + Examples + Code Samples — וזה בדרך כלל נעשה באופן ידני.

Fern יכול להפוך את ה-API Specification למקור שממנו נוצרים ה-SDKs וה-Documentation — כך שהעדכון קורה במקום אחד, ולא בעשרים מקומות בנפרד בכל פעם שה-API הפיננסי משתנה.

למי לפנות בחברת אשראי כזו: Head of API Product/Platform (ה-Lead), VP Engineering (תפקיד שני). סיגנל טוב לבדוק מראש: חיפוש ב-GitHub של "unofficial [שם החברה] SDK" — אם קיימים SDKs "לא רשמיים" שהקהילה בנתה, זה אומר שאין להם SDK רשמי טוב, וזה בדיוק הפער ש-Fern סוגר.

⠿
תרחיש שלישי: בנק
בנק עם חשיפת Open Banking / PSD2

הבנק חייב לחשוף APIs של מידע על חשבונות ויזמות תשלום ל-Third Party Providers (TPPs) ולפינטקים חיצוניים — לא כברירת מחדל עסקית, אלא כדרישה רגולטורית עם תאריך יעד.

הבעיה: תחת PSD2/PSD3, ה-API, ה-Docs וה-SDKs חייבים לעבור הסמכה (Certification) מול הרגולטור ומול כל TPP שמתחבר. כל Drift בין ה-Spec לתיעוד בפועל לא רק מעצבן — הוא יכול לגרום לכשל בהסמכה או לעיכוב שמונע משותף להתחבר בזמן.

Fern נותן תיעוד ו-SDKs שמסונכרנים אוטומטית מול ה-Spec הרגולטורי, מה שמקצר את זמן ההסמכה של TPP חדש ומקטין את הסיכון ל-Audit. וכאן, בניגוד לביטוח, Self-Hosted הוא לא רק "נחמד שיהיה" — במקרים רבים זו דרישה מפורשת של הרגולטור המקומי (Data Residency), לא נקודה למשא ומתן.

למי לפנות בבנק כזה: Head of Open Banking / Head of API Architecture (ה-Lead), Compliance/Risk (מעורבים מוקדם, לא בסוף). קיצור זמן ההסמכה מול TPPs הוא נקודת הכניסה הכי חזקה.

שאלת Discovery לסגירת התרחיש "כמה זמן לוקח היום מרגע שTPP חדש עובר את תהליך ההסמכה שלכם ועד שהאינטגרציה שלו רצה בפרודקשן?"

ההבחנה החשובה:

Governance / Management / Discovery → Postman. 

Consumption / Developer Experience → Fern. 

Fern לא מחליף את ה-API Catalog — הוא יושב במורד הזרם, השכבה הרחבה יותר סביב ה-APIs: קונטקסט עסקי, Guides, דוגמאות, Troubleshooting. 

אם הלקוח הוא לקוח Postman, Postman נשאר נקודת המגע הראשונה שלו.

ה-Sweet Spot האמיתי: לא חברה שמעולם לא חשבה על זה — חברה שכבר מנסה לפתור את זה בעצמה ומפגרת. Twilio, לדוגמה: 10 אנשים מתחזקים SDKs, 10 מתחזקים Docs, שני Major Versions מאחורי ה-OpenAPI שלהם — ובכל זאת חתמו על עסקה בת שישה ספרות. זה הסימן: מאמץ ידני גדול + תוצאה מפגרת.

Fern פותר את שני הצדדים — פיתוח מהיר יותר, פחות חיכוך בין צוותים. חשוב לזכור: AEO (הגלוי ל-AI חיצוני) רלוונטי רק ל-Docs פומביים — Docs פנימיים לא צריכים שמודלים "ילמדו" מהם, אבל עדיין מרוויחים מ-MCP עם Auth Passthrough, מ-llms.txt ומחיפוש AI פנימי.

"אנחנו לא צריכים AI Agents"
AEזה בסדר — Fern לא חייב להיות פרויקט AI. הערך המרכזי הוא Documentation, SDKs ו-Developer Experience. ה-AI/MCP הוא שכבת שימוש נוספת שיכולה להיות רלוונטית בהמשך.

תחרות

Mintlify — המתחרה הכי גדול. אג'נט-פרנדלי, אבל חסר לו הרבה

Mintlify כן Agent-friendly, ובונה agent-readiness בקצב דומה — אבל אין לו: Enterprise scale, Multi-repo, RBAC, Self-Hosting, ואין לו בכלל SDKs / CLIs / MCPs. זה תיעוד בלבד.

הטיעון המנצח: Fern הוא קו מוצרים מלא — Documentation, SDKs, CLI ו-MCP servers בפלטפורמה אחת, שבה ה-Docs מפנים אוטומטית לכל מה שעוד Fern מייצר. וגם: Fern מגובה על ידי Postman, חברה בשווי 5.5 מיליארד דולר, עם יותר הון וקצב Roadmap מהיר יותר.

תמחור

לפי מוצר, ומבוסס-ערך — לפי מורכבות ה-API, סקאלה (שטח פנים ל-API חיצוני, מספר Microservices לפנימי), וגודל/הכנסות החברה.

Documentation: מ-4,000$ (רצפת Enterprise) ועד 800,000$ לארגון גדול ומפוזר טכנולוגית. SDKs: רצפה דומה, עד 500,000$ לשפה, ומתומחרים בנפרד מה-Documentation. SDK ל-API פנימי מתומחר זול יותר מ-SDK ל-API חיצוני. הנחה: עד 50% ממחיר הליסט.

נקודת ייחוס: חברת Series B/C עם 200-500 Endpoints, ב-TypeScript + Python + Java, יוצאת בסביבות 30,000$ (כ-10,000$ לשפה). עסקאות בסקאלת NVIDIA (150-300 מוצרים, Parsing מורכב) הולכות הרבה יותר גבוה. תמיד להשתמש במחשבון התמחור לטווחים, ולהכניס Specialist לפני הצעת מחיר פורמלית.
