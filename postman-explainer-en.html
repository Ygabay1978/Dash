Explainer about POSTMAN Great. Give me 30 seconds to explain how companies deal with this today.
In large organizations, we often see different teams using Postman independently — through a mix of personal accounts and organizational accountsת without centralized management of users, permissions, workflows, APIs, or security.
Over time, this creates a situation where each team works a little differently.
There is no centralized view of the organization’s APIs and the activity around them, and it becomes difficult to know who is using what and who has access to which APIs and systemsת especially as activity becomes distributed across users, teams, accounts, and increasingly, AI tools and AI agents.
This is where topics like API Governance, standardization, and security typically start to become important.
You Know, Building APIs is no longer really the hard part. The challenge starts when APIs grow across multiple teams, products, and environments.
At that point, organizations typically face the same challenges:
limited visibility into what actually exists
Inconsistent documentation and testing
Duplicated work across teams, and growing Governance and security requirements.
More recently, AI initiatives have exposed these challenges even further, because AI applications depend on APIs that are discoverable, reliable, and properly documented.

This is exactly where Postman comes in. Postman is a comprehensive platform where teams can design, test, document, discover, and govern APIs, instead of managing all of this across disconnected tools and processes.
Whether you are at the prototype stage or scaling a system that is already in production, Postman provides tools across the API lifecycle
So yes — our solution is much more than just sending requests. We support the entire API lifecycle, from design and documentation to testing, automation, monitoring, and Governance.

Closing
Every development organization — whether it follows Waterfall, Agile, or CI/CD — goes through the same five stages in practice - Design, Develop, Test, Deploy and Monitor.
The question is whether those stages are connected or isolated.

The greatest value of Postman is typically in stages 1–3 — design, development, and testing — because this is where mistakes are the least expensive to fix. Deployment and monitoring add value further down the lifecycle, but they are not the core of what I want you to focus on today.

Our platform isn't meant to replace your API Gateway — unless you want it to — the value is in creating a layer of visibility, discovery, security, and Governance around your APIs, and managing their entire lifecycle more efficiently.

How It Works in Practice – General Overview
Every development organization - Waterfall, Agile, or CI/CD - actually goes through the five stages of Design, Develop, Test, Deploy and Monitor. The only question is whether they’re connected or isolated.
Postman provides end-to-end coverage across the entire API lifecycle through a Waterfall-style architecture, where each stage builds on what was defined in the previous stage — and the system automatically enforces it.
In the Design stage, teams define the API Contract, apply Governance rules, and use AI to create and refine Specs. At the same time, frontend teams can work with Mock APIs even before the backend is ready.
In the Development stage, we continuously verify that the code remains aligned with the defined API Contract, allowing teams to identify potentially breaking changes early.
In the Testing stage, teams can automatically generate and run tests, use AI to fix failing tests, and run Load Tests on their APIs.
In the Deployment & Monitoring stage, automated checks continue to verify that internal and external APIs meet the defined standards, while Insights identifies gaps based on real traffic.

At the same time, Agent Mode and AI Engineer provide context-aware AI capabilities that can take automatic or guided actions across these stages.
Agent Mode works with APIs, tests, and Governance workflows.
AI Engineer works with code and Git history to identify, for example, old or unused APIs, and to review changes before they are merged.
You can even build the Governance rules themselves using AI, and Postman then enforces them consistently across every project in the organization.

Postman provides the highest value around the design, development, and testing stages, because that’s where a mistake costs the least to fix. Deployment and monitoring are additional value we’ll add later, but they’re not the core of what I want you to see today.

Speed vs. Quality

Your developers are already using tools like Copilot or Cursor to write code — and that’s great for speed. The problem is that testing throughput doesn’t grow at the same pace. You get more code, but not more verification that it’s correct. And that’s exactly the gap that causes the spike in bugs reaching production.

APIs Built for Humans, Not AI Agents

Here's a point most companies don't think about at all: when an AI agent is the one consuming your API instead of a human developer, it needs a different kind of spec. An AI agent doesn't 'understand from context' like a developer does — it needs to be told explicitly which actions are possible and what their constraints are. If your API isn't written that way, the agent will simply misuse it — and you won't know until it happens in production.

Governance as the Bottleneck

And when everything runs faster, Governance and security become the organization's bottleneck. Audit evidence documentation turns from an ongoing process into a manual scramble once a quarter. And nobody wants to do that under pressure.

Fabric

Fabric is our central control layer for the AI world in the organization.⠿

As more teams start using different models — OpenAI, Claude, Gemini — to build AI agents and connect to MCP servers and internal APIs, each team starts managing its own connections, permissions, and credentials.
Fabric routes all of this traffic through a single control point, giving the organization visibility into where AI requests are going, which models and APIs they can access, how secrets are managed, how much it costs, and what actually happened — all under a unified governance layer.**

Example
You have one team working with OpenAI, another with Claude, and an agent connecting to an MCP server — and they all need access to internal systems. Today, each may have its own keys, permissions, and logs, with no central layer providing visibility across all the traffic.

Postman Passport

Passport is a central Governance layer for discovering, requesting access to, and securely consuming APIs across the organization.⠿

As the number of APIs grows, along with the number of people, applications, and AI agents that need to use them, it becomes increasingly difficult to know who is using what, who has access, and where API keys and secrets are being stored.
A developer searches for an API in Slack or documentation, requests access from someone, and the actual key ends up in .env files, scripts, CI/CD pipelines, and other places. As more AI agents start accessing APIs, this challenge only gets bigger.
So instead of giving developers and AI agents the actual API key and letting it spread across files, scripts, and CI/CD, they receive a Passport reference.

The actual credential stays in the customer’s existing Vault and is only resolved at the time of the API call. The organization gets full visibility into who requested access, who approved it, and how the API is being used — without exposing the actual secrets at any point.

Summary line
Passport gives the organization a central way to discover APIs, manage access to them, and enable secure use of them — without exposing the real Credentials.⠿
Example :
A new team is building an application that needs to use an internal customer API. The developer needs to figure out who owns the API, who to contact, get a key, and add it to the application.
Multiply that by dozens of APIs and hundreds of developers — and at some point, the organization no longer knows who has which key or who has access to which API.
Passport gives the organization a centralized way to discover APIs, manage access to them, and enable secure consumption — without exposing the actual credentials.**
 ⠿
How Passport Solves This⠿
  • Central Discovery — developers and AI Agents find approved APIs in one place.
  • Controlled Access Request — instead of getting the real Key, they get a Passport Reference.
  • Secretless Consumption — the real Credential stays in the customer’s existing Vault, and is only resolved at the actual moment of the API call — without the user or the Agent ever seeing or copying it.
  • Full Visibility — who requested access, who approved it, and how the API is actually used.
  • Works With Existing Tools — complements HashiCorp, AWS Secrets Manager, 1Password, etc., doesn’t replace them.

Common Customer Questions in a First Call⠿
"Do you connect to other systems (API Connect, Azure APIM)?"
"Yes. There are integrations with various gateways (including Azure API Management and IBM API Connect) and with AWS, Azure, and Google Cloud. Postman pulls information from existing environments for discovery and the API Catalog."
Remember: first clarify what the customer means by "integration" — discovery, monitoring, testing, or replacing a gateway.
⠿
"Is Postman a Gateway, or does it sit in the middle as one?"
"No. Postman isn't meant to replace your API Gateway. It connects to existing Gateways and pulls information from them, plus there's an agent that listens to activity in the environment."
Remember: keep the distinction clear — the Gateway handles traffic; Postman manages the API lifecycle around it.
⠿
"How do you find APIs that we ourselves don't know about?"
"A few discovery mechanisms: integration with gateways and cloud providers, an agent that identifies APIs from network traffic (Postman Insights), and service discovery in Kubernetes (Cluster Watcher). The goal is a broad picture of your entire API landscape."
Remember: this connects directly to the "unknown APIs" problem and the API Catalog.
⠿
"To monitor APIs, do you have to intercept traffic?"
"Not necessarily. With a Gateway integration, Postman gets information directly from the Gateway. There's also an agent option that listens to the environment and identifies which APIs are being called."
Remember: don't go too deep into the technology — there are a few methods depending on the customer's architecture.
⠿
"What is an API Catalog, and why do we need it if we have API Management?"
"API Catalog is a central registry giving you a single pane of glass over every API in the organization — what exists, who owns it, and what state it's in (linked to source control, CI/CD, and production). API Management handles real-time traffic; the Catalog gives you the visibility and ownership picture above it."
Remember: don't present the Catalog as "just another list" — it's visibility and ownership over a distributed API landscape.
⠿
"Do you work with source code and repositories?"
"Yes. There's a GitHub connection that links source code to APIs, and you can also turn existing code into Postman collections."
Remember: especially relevant for Git-based organizations.
⠿
"We work a lot with AI and Agents — how does Postman fit in?"
"Postman includes built-in AI capabilities (Postman AI and Agent Mode) that automate API development work — generating tests, docs, and workflows. Beyond that, as more AI/agent workflows consume APIs, the need grows for APIs that are discoverable, reliable, and well-documented, and for Governance once AI is part of the process."
Remember: first understand the customer's AI workflow, only then connect it to the relevant product.
⠿
"Do you enforce standards like OpenAPI on development teams?"
"Yes. Postman (API Governance) lets you define and enforce rules across teams — both built-in and custom rules — and plug Governance into CI/CD."
Remember: distinguish between "we follow OpenAPI" and "we actually enforce OpenAPI."

Numbers: Free 50 / Solo & Team 400 / Enterprise 800 (pooled), all per user/mo; overage: Solo $0.05, Team $0.04, Enterprise $0.035 per credit (Free: none, must upgrade).

"Postman doesn't compete with WAF/DDoS/authentication — it adds a security layer focused on the API lifecycle itself: Secret Scanner, which finds leaked secrets and keys in code and collections, security scorecards in the API Catalog, and a shift-left testing approach."
Remember: don't argue with the existing stack. Find out where the gaps actually are — lifecycle, Governance, secrets, and testing.

Remember: never promise a capability that hasn't actually been demonstrated — set up a technical follow-up with an SE.

Remember: start from what they're already doing with Postman, then identify what's missing around it.
