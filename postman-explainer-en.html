2. Governance and Managing APIs at Scale
In large organizations, we often see different teams using Postman independently — through personal accounts alongside organizational ones — with no centralized management of users, permissions, workflows, APIs, or security. Over time, this creates a situation where every team works a bit differently, there's no central picture of all the APIs and the activity around them, and it's hard to know who's using what and who holds access to which APIs and systems — especially as activity spreads across users, teams, accounts, and increasingly AI tools and AI Agents. This is usually where topics like API Governance, standardization, and security start coming up.
How I frame this "Our platform isn't meant to replace your API Gateway — unless you want it to — the value is in creating a layer of visibility, discovery, security, and Governance around your APIs, and managing their entire lifecycle more efficiently."
As we discussed, Postman provides end-to-end coverage across the whole API lifecycle through a waterfall-style architecture, where each stage builds on what was defined in the previous one — and enforces it automatically. In Design, teams define the API contract, apply Governance rules, and use AI to create and refine specs, while frontend teams can work against Mock APIs before the backend is ready. In Development, Postman continuously checks that the code stays aligned with the defined API contract, catching breaking changes early. In Testing, you can generate and run tests automatically, use AI to fix failing tests, and run load tests on your APIs. In Deployment & Monitoring, automated checks keep verifying that internal and external APIs meet the defined standards, while Insights identifies gaps based on real traffic. At the same time, Agent Mode and AI Engineer provide context-aware AI capabilities that can take automatic or guided action across these stages — Agent Mode works with APIs, tests, and Governance workflows, while AI Engineer works with code and Git history to identify, for example, old or unused APIs, and to review changes before they're merged. You can even build the Governance rules themselves with AI, and Postman then enforces them consistently across every project.

"Your developers are already using tools like Copilot or Cursor to write code — and that’s great for speed. The problem is that testing throughput doesn’t grow at the same pace. APIs Built for Humans, Not AI Agents

"Here's a point most companies don't think about at all: when an AI agent is the one consuming your API instead of a human developer, it needs a different kind of spec. An AI agent doesn't 'understand from context' like a developer does — it needs to be told explicitly which actions are possible and what their constraints are. If your API isn't written that way, the agent will simply misuse it — and you won't know until it happens in production."

Governance as the Bottleneck

"And when everything runs faster, Governance and security become the organization's bottleneck. Audit evidence documentation turns from an ongoing process into a manual scramble once a quarter. And nobody wants to do that under pressure."

Postman Passport

Passport is a central Governance layer for discovering, requesting access to, and securely consuming APIs across the organization.

The challenge I describe "As there are more APIs and more people, applications, and AI Agents that need to use them, it becomes hard to know who’s using what, who has access, and where the API Keys and Secrets end up scattered. A developer looks for an API on Slack or in documentation, requests access from someone, and the real Key ends up in .env files, scripts, CI/CD, and other places. And as more AI Agents start accessing APIs, this challenge only grows."
Example I give: A new team is building an application that needs an internal customer API. The developer needs to figure out who owns it, who to ask, get a Key, and plug it into the system. Multiply that by dozens of APIs and hundreds of developers — and at some point the organization no longer knows who holds which Key, and which API they have access to.
How Passport Solves This
  • Central Discovery — developers and AI Agents find approved APIs in one place.
  • Controlled Access Request — instead of getting the real Key, they get a Passport Reference.
  • Secretless Consumption — the real Credential stays in the customer’s existing Vault, and is only resolved at the actual moment of the API call — without the user or the Agent ever seeing or copying it.
  • Full Visibility — who requested access, who approved it, and how the API is actually used.
  • Works With Existing Tools — complements HashiCorp, AWS Secrets Manager, 1Password, etc., doesn’t replace them.
Summary line "Passport gives the organization a central way to discover APIs, manage access to them, and enable secure use of them — without exposing the real Credentials."

"Do you connect to other systems (API Connect, Azure APIM)?"
"Yes. There are integrations with various gateways (including Azure API Management and IBM API Connect) and with AWS, Azure, and Google Cloud. Postman pulls information from existing environments for discovery and the API Catalog."
Remember: first clarify what the customer means by "integration" — discovery, monitoring, testing, or replacing a gateway.
"Is Postman a Gateway, or does it sit in the middle as one?"
"No. Postman isn't meant to replace your API Gateway. It connects to existing Gateways and pulls information from them, plus there's an agent that listens to activity in the environment."
Remember: keep the distinction clear — the Gateway handles traffic; Postman manages the API lifecycle around it.
"How do you find APIs that we ourselves don't know about?"
"A few discovery mechanisms: integration with gateways and cloud providers, an agent that identifies APIs from network traffic (Postman Insights), and service discovery in Kubernetes (Cluster Watcher). The goal is a broad picture of your entire API landscape."
Remember: this connects directly to the "unknown APIs" problem and the API Catalog.
"To monitor APIs, do you have to intercept traffic?"
"Not necessarily. With a Gateway integration, Postman gets information directly from the Gateway. There's also an agent option that listens to the environment and identifies which APIs are being called."
Remember: don't go too deep into the technology — there are a few methods depending on the customer's architecture.
"What is an API Catalog, and why do we need it if we have API Management?"
"API Catalog is a central registry giving you a single pane of glass over every API in the organization — what exists, who owns it, and what state it's in (linked to source control, CI/CD, and production). Remember: don't present the Catalog as "just another list" — it's visibility and ownership over a distributed API landscape.
"Do you work with source code and repositories?"
"Yes. There's a GitHub connection that links source code to APIs, and you can also turn existing code into Postman collections."
Remember: especially relevant for Git-based organizations.
"We work a lot with AI and Agents — how does Postman fit in?"
"Postman includes built-in AI capabilities (Postman AI and Agent Mode) that automate API development work — generating tests, docs, and workflows. Beyond that, as more AI/agent workflows consume APIs, the need grows for APIs that are discoverable, reliable, and well-documented, and for Governance once AI is part of the process."
Remember: first understand the customer's AI workflow, only then connect it to the relevant product.
"Do you enforce standards like OpenAPI on development teams?"
"Yes. Postman (API Governance) lets you define and enforce rules across teams — both built-in and custom rules — and plug Governance into CI/CD."
Remember: distinguish between "we follow OpenAPI" and "we actually enforce OpenAPI."
"What does Postman add beyond the WAF, DDoS, and Authentication we already have?"
"Postman doesn't compete with WAF/DDoS/authentication — it adds a security layer focused on the API lifecycle itself: Secret Scanner, which finds leaked secrets and keys in code and collections, security scorecards in the API Catalog, and a shift-left testing approach."
Remember: don't argue with the existing stack. Find out where the gaps actually are — lifecycle, Governance, secrets, and testing.
"We work with MuleSoft — where does Postman fit in?"
"Postman doesn't replace MuleSoft as an integration platform — MuleSoft/Anypoint is its own integration platform with its own Catalog. The relevant angle is self-service API publishing from Postman, with Governance and an approval flow, which fills the gap of long waits to create new APIs. A direct, specific technical integration with MuleSoft hasn't been fully confirmed yet."
Remember: never promise a capability that hasn't actually been demonstrated — set up a technical follow-up with an SE.
"We already use Postman for testing — what else do we get?"
"Enterprise expands a point-solution use of testing into the full API lifecycle: design, Governance, and organization-wide visibility into every API in the company — not just the ones already being tested."
Remember: start from what they're already doing with Postman, then identify what's missing around it.
