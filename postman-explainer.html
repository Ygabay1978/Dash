לפני שניכנס ל-Postman, אשמח להבין קצת יותר עליך — מה התפקיד שלך ומה אתה מוביל היום אצלכם בחברה?

ואחרי שהוא עונה:

מעניין. ומה גרם לך לקבל את הפניה שלי לשיחה דווקא עכשיו? יש משהו ספציפי סביב API Testing או AI שאתם מנסים לפתור?

מעניין. כשאתה אומר את זה, אני סקרן להבין - זה משהו שכל צוות מתמודד איתו בפני עצמו, או שיש אצלכם איזושהי יוזמה רחבה יותר סביב APIs וסטנדרטיזציה? [Governance / API Catalog]

אם הוא מדבר על חוסר סטנדרטיזציה:

ואיך אתם מתמודדים עם זה היום? כלומר, כשצוות מפתח API חדש, מי מגדיר מה הסטנדרט ואיך מוודאים שהוא באמת עומד בו? [Governance]

אם הוא מדבר על חוסר Visibility:

זה מעניין. אז בעצם אין היום מקום אחד שבו אפשר לראות אילו APIs קיימים, מי הבעלים שלהם ואיך צוותים אחרים יכולים למצוא ולהשתמש בהם? [API Catalog / Passport]

להבין את תהליך הפיתוח והבדיקות

ואיך זה עובד היום בפועל? נניח שמפתח משנה API, מה קורה מהרגע הזה ועד שהשינוי מגיע לפרודקשן? כמה מזה כבר אוטומטי וכמה עדיין דורש עבודה ידנית? [Postman / Automation]

ואם הוא אומר שיש הרבה עבודה ידנית:

כן, זה מעניין. עם כל השימוש ב-AI היום, אני סקרן להבין - אצלכם ה-AI כבר מתחיל לעבוד גם מול APIs וכלים פנימיים, או שזה עדיין בעיקר סביב כתיבת קוד? [AI / Fabric / Fern]

אם הוא מדבר על Agents:

ואיך אתם שולטים במה שה-Agent יכול לגשת אליו? כלומר, איך הוא יודע לאיזה API או כלי מותר לו לגשת, ואיך אתם עוקבים אחרי זה? או איך אתם שולטים על עלויות? [Fabric / Passport]

אם עולה נושא של API Consumption, והבעיה היא שמפתחים לא יודעים למצוא/לקבל גישה ל-API:

ואיך מפתח מקבל היום גישה ל-API פנימי שהוא צריך? יש איזשהו מקום מרכזי שהוא יכול למצוא אותו ולבקש access, או שזה עדיין דרך Slack, tickets וכדומה? [Passport / API Catalog]

לקראת סוף השיחה:

אם אני רגע מסכם את מה שאמרת, הבעיה המרכזית היא יותר סביב XXX. מי אצלכם הכי קרוב לבעיה הזאת ביום־יום? מי בעצם יהיה האדם הנכון להכניס לשיחה הבאה? [Champion / Multithreading]

הסבר על POSTMAN "מצוין. תנו לי 30 שניות להסביר איך חברות מתמודדות עם זה היום. בניית APIs כבר לא באמת החלק הקשה. האתגר מתחיל כשה-APIs גדלים על פני כמה צוותים, מוצרים וסביבות.
בשלב הזה, ארגונים בדרך כלל נתקלים באותן בעיות: אין נראות למה שקיים בכלל, תיעוד ובדיקות לא עקביים, כפילויות עבודה בין צוותים, ודרישות Governance ואבטחה שגדלות כל הזמן.
בזמן האחרון, יוזמות AI חשפו את הבעיות האלה עוד יותר, כי אפליקציות AI תלויות ב-APIs שאפשר לגלות, שאמינים, ושמתועדים כמו שצריך.
זה בדיוק המקום שבו Postman נכנס לתמונה. Postman היא פלטפורמה כוללת שבה צוותים יכולים לעצב, לבדוק, לתעד, לגלות ולנהל Governance על APIs — במקום לנהל את כל זה על פני כלים ותהליכים מפוצלים.
בין אם אתם בשלב פרוטוטייפ לרעיון, ובין אם אתם מרחיבים מערכת שכבר בפרודקשן — Postman נותנת לכם את הכלים שאתם צריכים בכל שלב במחזור החיים של ה-API.
אז כן — הפתרון שלנו הוא הרבה יותר מרק שליחת requests. אנחנו מלווים את כל מחזור החיים של ה-API, מהעיצוב והתיעוד ועד למעקב, אוטומציה ו-Governance."

2. Governance וניהול APIs בארגון בקנה מידה
בארגונים גדולים אנחנו רואים לא מעט מקרים שבהם צוותים שונים משתמשים ב-Postman באופן עצמאי, דרך חשבונות אישיים לצד חשבונות ארגוניים, בלי ניהול מרכזי של המשתמשים, ההרשאות, תהליכי העבודה, ה-APIs והאבטחה. עם הזמן, זה יוצר מצב שבו כל צוות עובד קצת אחרת, אין תמונה מרכזית של כלל ה-APIs והפעילות סביבם, וקשה לדעת מי משתמש במה ומי מחזיק גישה לאילו APIs ומערכות — במיוחד כשהפעילות מפוזרת בין משתמשים, צוותים, חשבונות, ויותר ויותר גם כלי AI ו-AI Agents. זה המקום שבו בדרך כלל מתחילים לעלות נושאים כמו API Governance, סטנדרטיזציה ואבטחה.
איך אני ממסגר את זה "הפלטפורמה שלנו לא נועדה להחליף את ה-API Gateway — אלא אם תרצו בכך — הערך הוא ביצירת שכבת שיקוף, גילוי, אבטחה ו-Governance סביב ה-APIs, ובניהול יעיל יותר של כל מחזור החיים שלהם."
כפי שדיברנו, Postman נותנת מענה כולל לאורך כל מחזור החיים של ה-API באמצעות ארכיטקטורת מפל, שבה כל שלב מתבסס על מה שהוגדר בשלב הקודם, וגם אוכף אותו אוטומטית: בעיצוב (Design) מגדירים את חוזה ה-API ומיישמים Governance; בפיתוח (Development) בודקים ברציפות שהקוד נשאר בהתאם לחוזה ומזהים שינויים ששוברים מערכות קיימות; בבדיקות (Tests) מייצרים ומריצים בדיקות אוטומטית, עם AI שמתקן בדיקות שנכשלו ומריץ בדיקות עומס; ובהטמעה ומעקב (Deployment & Monitoring) בדיקות אוטומטיות ממשיכות לוודא עמידה בסטנדרטים, ו-Insights מזהה פערים על בסיס תעבורה אמיתית. במקביל, Agent Mode ו-AI Engineer מספקים יכולות AI שמבינות את ההקשר ומבצעות פעולות אוטומטיות או מונחות לאורך השלבים — Agent Mode עובד עם APIs, בדיקות ותהליכי Governance, ו-AI Engineer עובד עם הקוד וההיסטוריה ב-Git כדי לזהות APIs ישנים או לא בשימוש, ולבדוק שינויים לפני Merge. אפשר גם ליצור את כללי ה-Governance עצמם בעזרת AI, ו-Postman אוכפת אותם באופן עקבי על פני כל הפרויקטים.
מה כולל Postman Enterprise
תוכנית ה-Enterprise מיועדת לארגונים שרוצים לנהל APIs בקנה מידה רחב — Governance ארגוני, בקרות אבטחה ונראות מלאה, אכיפת כללים אוטומטית על פני כל הצוותים, ניהול סודות מרכזי, ותצוגה אחודה של כל ה-APIs שנבנים בארגון. בקנה מידה גדול, כלים מפוזרים ותהליכים ידניים הופכים לסיכון ממשי, במיוחד לנוכח דרישות אבטחה ותאימות שהולכות וגדלות.
  • API Catalog — מקום מרכזי לראות ולנהל את כל ה-APIs, כולל אלה שבפיתוח ולא רק אלה שבפרודקשן.
  • API Governance — הגדרת סטנדרטים וכללים ל-APIs ואכיפתם לאורך הפיתוח וה-CI/CD.
  • Private API Network — קטלוג פנימי שמאפשר למפתחים למצוא ולצרוך APIs מאושרים של הארגון.
  • Advanced RBAC ובקרות ארגוניות — שליטה מדויקת על מי יכול לראות, לערוך, לפרסם ולגשת ל-APIs ולמידע.
  • Audit Logs, Reporting ו-API usage visibility — שקיפות מלאה על מי עשה מה, מתי, ואיך משתמשים ב-APIs.
  • Private Test and Flows Runners — הרצת בדיקות ו-Flows בתוך הסביבה הפרטית של הארגון, בלי לשלוח מידע לחוץ.
  • Insights — תמונה ברורה של פעילות ה-APIs, שימוש, תעבורה ודפוסי פעילות.
  • AI Capabilities — יכולות מבוססות AI שמסייעות למפתחים ולצוותים בתהליכים שונים לאורך מחזור החיים של ה-API, כולל Design, Testing, Documentation, Governance, and Development.
  • 800 קרדיטי AI משותפים למשתמש/חודש — קרדיטים חודשיים ליכולות ה-AI, משותפים בתוך הארגון.
כמה יכולות נוספות שיכולות להיות רלוונטיות, בהתאם לצרכי הלקוח:

Advanced Security Administration (ASA) — תוסף שמוסיף שכבת אבטחה ושליטה מתקדמת: Domain Capture, Account Discovery ו-Control, נראות ארגונית על Secret Scanner, אינטגרציה עם Azure Key Vault, AWS Secrets Manager ו-HashiCorp Vault, ו-BYOK.

Passport — תוסף שמתמקד באיך מפתחים, אפליקציות ו-AI Agents מוצאים APIs בארגון ומקבלים אליהם גישה — במקום לשאול ב-Slack מי יכול לשלוח API Key ולשמור אותו בקוד, מקבלים תהליך מסודר: למצוא, לבקש גישה, לקבל אישור, ולהשתמש בצורה מאובטחת, בלי לקבל את ה-Secret עצמו. Passport לא מחליף את ה-Vault הקיים, אלא מוסיף שכבת Discovery ו-Governance סביב הגישה והצריכה של APIs.

Fabric — שכבת בקרה מרכזית לעולם ה-AI בארגון. ככל שיותר צוותים עובדים עם מודלי LLM שונים, בונים AI Agents ומחברים AI למערכות פנימיות, Fabric נותן שכבה מרכזית לשלוט בתעבורה הזו, לאבטח אותה, להגדיר מה Agents יכולים לגשת אליו, לנהל Credentials, ולשלוט בעלויות ובצריכת Tokens. הוא לא בא להחליף את ה-API Gateway הקיים, אלא מוסיף שכבת Governance ייעודית לעולם ה-AI.

Fern — פלטפורמה נפרדת (נרכשה על ידי Postman בינואר 2026) שהופכת API קיים ל-Developer Experience מלא: מייצרת אוטומטית תיעוד, SDKs בשפות מרכזיות, CLI ו-MCP servers מתוך אותה הגדרת API אחת, כך שהם לא יוצאים מסונכרון אלה מאלה. פונה לצד ה-Consumption (איך צורכים את ה-API), לא לצד ה-Governance - ונמכרת כרגע כמוצר עצמאי, לא כחלק מחבילת Postman.

2 ה-AI: הנקודה שכל לקוח היום רוצה לדבר עליה

זה החלק שאני נותן לו הכי הרבה זמן בשיחה — כי זה מה שמעסיק כל CTO, VP Engineering ו-CISO שאני נפגש איתו ב-2026.


"אני רוצה לעצור רגע על ולדבר על ה-AI, כי זה בעצם זאת נקודה מכרעת היום כמעט לכל ארגון. ה-AI לא משנה את חמשת השלבים האלה, אלא רק מגדיל בטירוף את המהירות שעוברים בהם. וכשהמהירות עולה, כל סדק שהיה קיים אצלכם גם קודם, נהיה גדול יותר, ומהר יותר."
מהירות מול איכות

"המפתחים שלכם כבר משתמשים בכלים כמו Copilot או Cursor לכתוב קוד — וזה מעולה למהירות. הבעיה היא שקצב הבדיקות לא גדל באותו הקצב. אתם מקבלים יותר קוד, אבל לא יותר וידוא שהוא תקין. וזה בדיוק הפער שגורם לזינוק בתקלות שמגיעות לפרודקשן."

APIs שנבנו לבני אדם, לא לסוכני AI

"יש נקודה שרוב החברות לא חושבות עליה בכלל: כשסוכן AI הוא זה שצורך את ה-API שלכם ולא מפתח אנושי, הוא צריך מפרט אחרת. סוכן AI לא 'מבין לפי הקשר' כמו מפתח — הוא צריך שיוצהר לו במפורש אילו פעולות אפשריות ומה המגבלות שלהן. אם ה-API שלכם לא כתוב כך, הסוכן פשוט ישתמש בו לא נכון — ואתם לא תדעו את זה עד שזה יקרה בפרודקשן."

Governance כבקבוק צוואר

"וכשהכל רץ מהר יותר, Governance ואבטחה נהיים בקבוק הצוואר של הארגון. תיעוד ראיות לביקורת — audit evidence — הופך מתהליך שוטף לריצה ידנית פעם ברבעון. ואת זה אף אחד לא רוצה לעשות בלחץ."

נתון שאני פותח איתו

"89 אחוז מהמפתחים כבר משתמשים ב-AI לכתיבת קוד. רק 24 אחוז מהם בכלל מעצבים את ה-API שלהם כך שסוכן AI יידע להשתמש בו נכון. זה הפער שאנחנו סוגרים."

איך אני ממשיך לחלק ה-AI של המוצר שלנו עצמו "וזה מוביל אותי לנקודה שהלקוחות שלנו הכי אוהבים: ה-AI שבתוך Postman הוא לא כמו ChatGPT כללי. אנחנו קוראים לו Agent Mode  והוא בנוי במיוחד לעולם ה-API. 
הוא רץ בתוך הסביבה שלכם ב-Postman, מכיר את כל הפרויקטים, הבדיקות וההתראות שכבר קיימים אצלכם, ולא רק עונה על שאלות אלא גם מבצע פעולות בפועל: כותב חוזים חדשים, מתקן בדיקות שנשברו, ומזהה מתי גרסה חדשה שוברת הבטחה שנתנו למישהו בעבר.

יש גם AI Engineer, שמתחבר למקום שבו שמור כל הקוד וההיסטוריה שלו (Git) ועושה עבודה עצמאית יותר/
לדוגמה, לעבור על כל ה-API-ים שלכם ולסמן אילו מהם כדאי להוציא משימוש כי הם ישנים או לא בשימוש, או לבדוק אוטומטית כל שינוי קוד חדש שמפתח מעלה למערכת, לפני שהוא מתקבל. 
ואתם יכולים גם לבנות את כללי ה-Governance עצמם בעזרת AI — לכתוב אותם ב-Claude או ב-ChatGPT, ו-Postman הוא זה שבפועל אוכף אותם אוטומטית, על כל הפרויקטים, כל הזמן. 
וזה בעצם ההבדל האמיתי: אתם יכולים לעשות חלק מזה בעצמכם, או לקנות כמה כלים נפרדים — אבל אנחנו שמים את הכל תחת קורת גג אחת."

3 מה יש לנו להציע - שלב-שלב

"זה מה שאני קורא ה-golden path: בכל שלב יש כלי שאוכף אוטומטית את מה שהגדרנו בשלב הקודם - כך שאתם לא בודקים את זה שוב מאוחר יותר."

01 · עיצוב

"אתם כותבים מראש מה ה-API אמור לעשות — כמו חוזה מסודר לפני שמתחילים לבנות בפועל — ויש AI שעוזר לכתוב ולתקן את החוזה הזה. אפשר גם להגדיר כלל כמו 'כל בקשה חייבת אישור זהות', וזה לא נשאר המלצה שמישהו צריך לזכור לבדוק — הוא נאכף אוטומטית. ובזמן שצוות ה-backend עדיין בונה את המערכת האמיתית, צוות ה-frontend יכול כבר להתחיל לעבוד מול גרסה מדומה שמתנהגת כמו ה-API האמיתי (Mock Server), כדי שלא יצטרכו לחכות."

02 · פיתוח

"כל פעם שמפתח כותב קוד, יש לנו כלי שרץ ברקע ובודק אוטומטית שהקוד עדיין עומד בחוזה שהוגדר בשלב העיצוב — ממש כמו בודק איות שרץ בזמן שאתה כותב מסמך, רק שהוא בודק לוגיקה ולא שגיאות כתיב. ואם מישהו משנה משהו שהולך לשבור הבטחה שמישהו אחר כבר סומך עליה — זה נתפס באותו רגע, לפני שהקוד בכלל נכנס למוצר, ולא כמו בדיקה מסורתית שמגלים את זה שבועיים אחר כך."

03 · בדיקות

"יש כלי שמריץ אוטומטית חבילה שלמה של בדיקות בלחיצת כפתור, ויש עוזר AI שבונה בדיקות בסיסיות ישירות מהחוזה שכתבתם בשלב העיצוב, ואפילו מתקן בדיקה שנשברה. ואפשר גם לבדוק מה קורה בעומס גבוה — למשל מה יקרה אם בבת אחת יהיו הרבה יותר משתמשים, כמו ביום מבצע גדול."

04–05 · פריסה ומעקב

"יש בדיקות אוטומטיות שרצות כל הזמן על ה-API-ים שפונים לעולם החוץ, כדי לוודא שהם באמת עונים ועובדים. יש גרסה מקבילה שרצה בתוך הרשת הפנימית שלכם, מאחורי כל שכבות האבטחה, ל-API-ים שלא פתוחים לעולם. ו-Insights מזהה פערים על סמך התעבורה האמיתית שקורית בפועל."

"שני דברים חשוב שתדעו — הם לא שייכים לשלב אחד, הם רצים על פני כולם: 
API Catalog נותן לכם תצוגה אחת של כל ה-APIs שבפיתוח בארגון — לא רק אלה שכבר חיים ב-gateway בפרודקשן. זה ההבדל המרכזי בינינו ל-Kong, Apigee או Boomi — הם מראים לכם רק מה שכבר רץ, אנחנו מראים לכם גם מה שבבנייה.
 וAgent Mode עם AI Engineer זמינים בכל שלב — לא עוזרים כלליים, אלא כלים שמכירים את הקונטקסט שלכם ובפועל מבצעים פעולות."

Agent Mode — עוזר AI מובנה
"זה לא עוזר כללי כמו ChatGPT — הוא בנוי במיוחד לעולם ה-API, ורץ בתוך הסביבה שלכם ב-Postman, ומכיר את כל הפרויקטים, הבדיקות וההתראות שכבר קיימים אצלכם. מפתח מבקש 'תבדוק אם הגרסה הזו שוברת הבטחה שנתנו למישהו בגרסה הקודמת' — Agent Mode לא רק עונה, הוא בפועל מריץ את ההשוואה על הקוד האמיתי ומראה תוצאה."
Native Git Workflows — עבודה טבעית עם Git
"בדיוק כמו ש-Google Docs שומר גרסאות קודמות של מסמך, ומאפשר לכמה אנשים לעבוד עליו במקביל בלי לדרוס אחד את השני — כך גם אנחנו מנהלים גרסאות על מפרטי ה-API עצמם, באותה שיטה שמפתחים מכירים מניהול קוד (Git). שני מפתחים יכולים לשנות את אותו מפרט במקביל, כל אחד בגרסה נפרדת שלו, ולשלב את השינויים בסוף בלי לאבד שום דבר."
CLI ואינטגרציית Pipeline
"אלה ממש אותן הבדיקות שרצות גם כשמפתח בודק את זה ידנית על המחשב שלו, וגם כשהמערכת האוטומטית שמעלה את הקוד לייצור מריצה אותן שוב, בלי מגע ידיים (בעולם הטכני זה נקרא CI/CD). אז אין מצב של 'עבד לי אצלי במחשב' ואז זה נשבר בשרת — זו בדיוק אותה בדיקה, פעמיים."

"מדמים API שלם בלי backend אמיתי, כדי שצוות frontend יתחיל לעבוד לפני שהקוד האמיתי בכלל קיים. הם צריכים מסך שמציג תשלומים, וה-backend עדיין באמצע הפיתוח — Mock Server מחזיר תשובות מדומות לפי המפרט, והעבודה מתקדמת במקביל."
Partner Workspaces — סביבות עבודה לשותפים
"שיתוף פעולה מאובטח עם צדדים שלישיים על API-ים משותפים, עם הרשאות מדויקות למה שהם רואים ומה שהם יכולים לשנות. חברת סליקה משתפת עם שותף חיצוני רק את ה-collection הרלוונטי, בלי לחשוף לו את ה-workspace הפנימי."
Advanced Security Administration — ASA
"זה ה-Add-on שאני מביא לשולחן כשמדברים על אבטחה בקנה מידה Enterprise, ומוצר קיים ופעיל היום. בגדול, זה נותן לצוות האבטחה שליטה מדויקת יותר על מי יכול להתחבר, מאיפה, ואיך שומרים על הסודות (secrets) שלהם — כולל ניתוב אוטומטי של כניסות לפי דומיין (Domain Capture), לוח בקרה והתראות על ניסיונות חשיפה של סודות (Secret Scanner), חיבור לכספות חיצוניות שהם כבר עובדים איתן — כמו Azure Key Vault, HashiCorp, AWS Secrets Manager, 1Password — והצפנה במפתח שהם עצמם שולטים בו (BYOK). ארגון עם דרישת רגולציה להצפין את המידע שלו במפתח שהוא שולט בו לגמרי — BYOK מאפשר את זה בלי לתת ל-Postman גישה למפתח ההצפנה."
Fabric — שכבת בקרה ל-AI (הרחבה בפאנל הצדדי)
"Fabric הוא שכבת הבקרה המרכזית שלנו לעולם ה-AI בארגון. ככל שיותר צוותים עובדים עם מודלים שונים, בונים AI Agents ומתחברים לשרתי MCP ול-APIs פנימיים — כל צוות מתחיל לנהל בעצמו את החיבורים, ההרשאות וה-Credentials שלו. Fabric

Fabric הוא שכבת הבקרה המרכזית שלנו לעולם ה-AI בארגון.

ככל שיותר צוותים מתחילים להשתמש במודלים שונים — OpenAI, Claude, Gemini — לבנות AI Agents, ולהתחבר לשרתי MCP ול-APIs פנימיים, כל צוות מתחיל לנהל בעצמו את החיבורים, ההרשאות וה-Credentials שלו.
Fabric מרכז את כל התעבורה הזו דרך נקודת שליטה אחת, כדי שהארגון יידע לאן בקשות ה-AI נשלחות, לאילו מודלים ו-APIs יש להן גישה, איך נשמרים הסודות, כמה זה עולה, ומה קרה בפועל - הכל תחת Governance אחיד.
מה Fabric מאפשר לארגון
  • נקודת שליטה מרכזית — לנהל ממקום אחד את התעבורה בין מודלים, Agents, שרתי MCP ו-APIs פנימיים.
  • Routing ו-Reliability — לנתב בקשות בין מודלים, לבצע Fallback אוטומטי כשמודל נופל, ולבחור את המודל המתאים לכל בקשה.
  • Security ו-Credential Management — ה-Agent לא צריך לראות או להחזיק את המפתחות בעצמו.
  • Agent Governance — לקבוע במדויק לאילו APIs, Tools או MCP Servers כל Agent מורשה לגשת.
  • שליטה בעלויות — לראות מי צורך כמה Tokens ובאיזו עלות, ולהגדיר תקציבים.
  • Audit מלא — לדעת מי הפעיל איזה Agent, על איזה מודל, לאיזה API ניגש, ואיזו Policy הופעלה.
3 דוגמאות מהשטח
  • בנק — כמה צוותים בונים AI Agents שונים (הלוואות, שירות לקוחות, ציות) עם מודלים שונים; Fabric נותן שכבת בקרה אחת לכולם.
  • חברת כרטיסי אשראי — Agent שבודק חשד להונאה צריך גישה ל-APIs פנימיים; Fabric קובע מה הוא יכול לגשת אליו ועוקב אחרי כל קריאה.
  • חברת ביטוח — כמה סוכני AI לחיתום תביעות רצים על מודלים שונים (GPT, Claude); Fabric מנתב ומאבטח את כל התעבורה במקום אחד.
משפט סיכום Fabric הוא שכבת הבקרה המרכזית שמחברת בין ה-AI, ה-Agents, שרתי MCP וה-APIs של הארגון — ונותנת שליטה על התעבורה, האבטחה, ההרשאות, העלויות וה-Audit, במקום שכל אחד מהם ינוהל בנפרד.
Postman Passport

Passport הוא שכבת Governance מרכזית לגילוי, בקשת גישה וצריכה מאובטחת של APIs בארגון.

האתגר שאני מתאר "ככל שיש יותר APIs ויותר אנשים, אפליקציות ו-AI Agents שצריכים להשתמש בהם, קשה לדעת מי משתמש במה, למי יש גישה, ולאן ה-API Keys וה-Secrets מתפזרים. מפתח מחפש API ב-Slack או בתיעוד, מבקש גישה ממישהו, וה-Key האמיתי מגיע לקבצי .env, לסקריפטים, ל-CI/CD ולעוד מקומות."
דוגמה: צוות חדש בונה אפליקציה שצריכה API פנימי של לקוחות. המפתח צריך להבין מי הבעלים, למי לפנות, לקבל Key ולהכניס אותו למערכת. תכפילו את זה בעשרות APIs ומאות מפתחים — ובשלב מסוים הארגון כבר לא יודע מי מחזיק איזה Key, ולאיזה API יש לו גישה. Passport נותן לארגון דרך מרכזית לגלות APIs, לנהל את הגישה אליהם ולאפשר שימוש מאובטח בהם — בלי לחשוף את ה-Credentials האמיתיים.
איך Passport פותר את זה
  • גילוי מרכזי — מפתחים ו-AI Agents מוצאים APIs מאושרים במקום אחד.
  • בקשת גישה מבוקרת — במקום לקבל את ה-Key האמיתי, מקבלים Reference של Passport.
  • Secretless Consumption — ה-Credential האמיתי נשאר ב-Vault הקיים של הלקוח, ונפתר רק בזמן הקריאה בפועל ל-API — בלי שהמשתמש או ה-Agent רואים או מעתיקים אותו.
  • Visibility מלא — מי ביקש גישה, מי אישר, ואיך בפועל משתמשים ב-API.
  • עובד עם הכלים הקיימים — משלים HashiCorp, AWS Secrets Manager, 1Password וכו', לא מחליף אותם.
3 דוגמאות מהשטח
  • בנק — מפתח צריך API לבדיקת יתרות; במקום לחפש ב-Slack, הוא מוצא אותו ב-Passport ומקבל גישה מאובטחת.
  • חברת כרטיסי אשראי — שותף חוץ-ארגוני שצריך API לעיבוד תשלומים מקבל Reference דרך Passport, בלי לקבל את ה-Key האמיתי.
  • חברת ביטוח — AI Agent שבודק פוליסות צריך גישה ל-API פנימי; Passport מנהל את הבקשה, האישור וה-Audit.

Advanced Security Administration — ASA

ASA הוא ה-Add-on שרלוונטי לאבטחה בקנה מידה Enterprise.

בגדול, זה נותן לצוות האבטחה שליטה מדויקת יותר על מי יכול להתחבר, מאיפה, ואיך שומרים על הסודות (secrets) שלהם. ברירת המחדל של Postman כבר מאובטחת, אבל ASA מוסיף שכבת בקרה נוספת שספציפית ל-Enterprise ולדרישות רגולציה כמו SOC 2, ISO או PCI.
הוא גם כולל: ניתוב אוטומטי של כניסות לפי דומיין (Domain Capture), לוח בקרה והתראות על ניסיונות חשיפה של סודות (Secret Scanner), חיבור לכספות חיצוניות כמו Azure Key Vault, HashiCorp, AWS Secrets Manager, 1Password, והצפנה במפתח שהלקוח עצמו שולט בו (BYOK).
מה כלול ב-ASA
  • Domain Capture — ניתוב אוטומטי של כניסות לפי דומיין, כך שכל עובד נכנס לחשבון הארגוני הנכון בלי בלבול בין חשבונות אישיים לחשבון החברה.
  • Secret Scanner — לוח בקרה והתראות — לא רק סורק סודות בודד, אלא תמונת מצב ארגונית: כמה ניסיונות חשיפה קרו, איפה, ומי היה מעורב.
  • אינטגרציה עם כספות חיצוניות — Azure Key Vault, HashiCorp, AWS Secrets Manager, 1Password — כדי ש-Postman יעבוד עם התשתית שהלקוח כבר משתמש בה, לא יחליף אותה.
  • BYOK — הצפנה במפתח של הלקוח — הלקוח שולט לגמרי במפתח ההצפנה; Postman לא מקבל אליו גישה בשום שלב.
3 דוגמאות מהשטח
  • בנק — רגולציה מחייבת BYOK; הבנק שולט לגמרי במפתח ההצפנה, ו-Postman לא מקבל אליו גישה.
  • חברת כרטיסי אשראי — Secret Scanner מזהה שמפתח API דלף לריפו ציבורי ומתריע מיידית.
  • חברת ביטוח — Domain Capture מבטיח שכל עובד נכנס לחשבון הארגוני הנכון, לא לחשבון אישי.
דוגמה שאני נותן: ארגון פיננסי שכפוף לרגולציה שמחייבת אותו להצפין את כל המידע הרגיש שלו במפתח שהוא עצמו שולט בו, ולא סומך על אף ספק חיצוני שמחזיק את המפתח. עם BYOK, הארגון שומר את מפתח ההצפנה בכספת שלו — ו-Postman פשוט לא יכול לגשת למידע בלי המפתח הזה, אפילו אם הוא ירצה.
משפט סיכום "ASA לא מחליף את האבטחה הבסיסית של Postman — הוא מוסיף עליה שכבת בקרה, ניראות ושליטה ברמת Enterprise, למי שצריך לעמוד בדרישות רגולציה מחמירות."
Fern

Free מול Enterprise Hosting — מה זה אומר בפועל
ההבדל בפשטות תחשוב על זה כמו מנהל מרכזי ויחידות ביצוע. ב-Free, גם ה-Control Plane (ניהול והגדרות) וגם ה-Data Plane (עיבוד והעברת הנתונים בפועל) פועלים בענן של Postman — הדרך המהירה ביותר להגיע ל-Production. ב-Enterprise, ה-Control Plane נשאר בענן Postman, אבל הלקוח מריץ את רכיבי ה-Data Plane בענן הפרטי שלו — לשליטה במיקום הנתונים (Data Residency) ובידוד רשת.
  • מתי זה שווה את הכסף — אם הארגון כבר בענן Postman ואין לו מגבלת מיקום נתונים: כנראה שאין יתרון משמעותי. אם הוא חייב שהעיבוד יתבצע בענן שלו, דורש בידוד רשת, או כפוף לרגולציה/מדיניות אבטחה ספציפית: Enterprise עשוי להיות ממש רלוונטי.
  • נקודה חשובה לציין ללקוח — "Data Residency" לא אומר שכל הנתונים נשארים אצל הלקוח — ה-Control Plane עדיין בענן Postman. שווה לבדוק בכל מוצר ספציפי אילו נתונים עוברים בין הרכיבים, ומה בדיוק נשאר בצד הלקוח, לפני שמציגים את זה כסיבה לשדרג.
