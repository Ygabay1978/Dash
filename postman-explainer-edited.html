הסבר על POSTMAN
בארגונים גדולים אנחנו רואים לא מעט מקרים שבהם צוותים שונים משתמשים ב-Postman באופן עצמאי, דרך חשבונות אישיים לצד חשבונות ארגוניים, בלי ניהול מרכזי של המשתמשים, ההרשאות, תהליכי העבודה, ה-APIs והאבטחה. עם הזמן, זה יוצר מצב שבו כל צוות עובד קצת אחרת, אין תמונה מרכזית של כלל ה-APIs והפעילות סביבם, וקשה לדעת מי משתמש במה ומי מחזיק גישה לאילו APIs ומערכות — במיוחד כשהפעילות מפוזרת בין משתמשים, צוותים, חשבונות, ויותר ויותר גם כלי AI ו-AI Agents. זה המקום שבו בדרך כלל מתחילים לעלות נושאים כמו API Governance, סטנדרטיזציה ואבטחהבניית APIs כבר לא באמת החלק הקשה. האתגר מתחיל כשה-APIs גדלים על פני כמה צוותים, מוצרים וסביבות.
בשלב הזה, ארגונים בדרך כלל נתקלים באותן בעיות: אין נראות למה שקיים בכלל, תיעוד ובדיקות לא עקביים, כפילויות עבודה בין צוותים, ודרישות Governance ואבטחה שגדלות כל הזמן.
בזמן האחרון, יוזמות AI חשפו את הבעיות האלה עוד יותר, כי אפליקציות AI תלויות ב-APIs שאפשר לגלות, שאמינים, ושמתועדים כמו שצריך.
זה בדיוק המקום שבו Postman נכנס לתמונה. Postman היא פלטפורמה כוללת שבה צוותים יכולים לעצב, לבדוק, לתעד, לגלות ולנהל Governance על APIs — במקום לנהל את כל זה על פני כלים ותהליכים מפוצלים.
בין אם אתם בשלב פרוטוטייפ לרעיון, ובין אם אתם מרחיבים מערכת שכבר בפרודקשן — Postman נותנת לכם את הכלים שאתם צריכים בכל שלב במחזור החיים של ה-API.
אז כן — הפתרון שלנו הוא הרבה יותר מרק שליחת requests. אנחנו מלווים את כל מחזור החיים של ה-API, מהעיצוב והתיעוד ועד למעקב, אוטומציה ו-Governance.

 איך זה עובד בפועל – סקירה כללית
כל ארגון פיתוח — בין אם הוא עובד במודל Waterfall, Agile או CI/CD — עובר בפועל את אותם חמישה שלבים:
Design → Develop → Test → Deploy → Monitor
השאלה היא האם השלבים האלה מחוברים זה לזה או מבודדים אחד מהשני.

הערך המרכזי של Postman נמצא בדרך כלל בשלבים 1–3 — Design, Development ו-Testing — מכיוון שזה השלב שבו הכי זול לתקן טעויות. Deployment ו-Monitoring מוסיפים ערך בשלבים המאוחרים יותר של מחזור החיים, אך הם אינם הליבה שעליה אני רוצה שתתמקדו היום.

Postman מספק כיסוי מקצה לקצה לאורך כל מחזור החיים של ה-API, באמצעות ארכיטקטורה בסגנון Waterfall, שבה כל שלב מתבסס על מה שהוגדר בשלב הקודם — והמערכת אוכפת זאת באופן אוטומטי.

בשלב ה-Design, הצוותים מגדירים את חוזה ה-API (API Contract), מחילים כללי Governance ומשתמשים ב-AI כדי ליצור ולשפר את ה-Specs. במקביל, צוותי ה-Frontend יכולים לעבוד עם Mock APIs עוד לפני שה-Backend מוכן.
בשלב ה-Development, אנחנו מוודאים באופן רציף שהקוד נשאר תואם ל-API Contract שהוגדר, וכך מאפשרים לצוותים לזהות שינויים שעלולים לשבור תאימות כבר בשלב מוקדם.
בשלב ה-Testing, הצוותים יכולים ליצור ולהריץ בדיקות באופן אוטומטי, להשתמש ב-AI כדי לתקן בדיקות שנכשלו, ולהריץ Load Tests על ה-APIs שלהם.
בשלבי ה-Deployment וה-Monitoring, בדיקות אוטומטיות ממשיכות לוודא ש-APIs פנימיים וחיצוניים עומדים בסטנדרטים שהוגדרו, בעוד ש-Insights מזהה פערים על בסיס תעבורת API אמיתית.

במקביל, Agent Mode ו-AI Engineer מספקים יכולות AI מבוססות-הקשר שיכולות לבצע פעולות אוטומטיות או מונחות לאורך השלבים השונים.
Agent Mode עובד עם APIs, בדיקות ותהליכי Governance.
AI Engineer עובד עם הקוד ועם היסטוריית Git כדי לזהות, לדוגמה, APIs ישנים או שאינם בשימוש, ולבדוק שינויים לפני שהם מתמזגים בקוד.
ניתן אפילו להשתמש ב-AI כדי לבנות את חוקי ה-Governance עצמם, ולאחר מכן Postman אוכף אותם באופן עקבי בכל הפרויקטים בארגון.

סיכום
Postman מספק את הערך הגבוה ביותר סביב שלבי ה-Design, Development וה-Testing, מכיוון שזה השלב שבו עלות התיקון של טעות היא הנמוכה ביותר.
הפלטפורמה שלנו לא נועדה להחליף את ה-API Gateway שלכם — אלא אם תרצו בכך.
הערך של Postman הוא ביצירת שכבה של Visibility, Discovery, Security ו-Governance סביב ה-APIs שלכם, ובניהול יעיל יותר של כל מחזור החיים שלהם.

מה כולל Postman Enterprise⠿

תוכנית ה-Enterprise מיועדת לארגונים שרוצים לנהל APIs בקנה מידה רחב — Governance ארגוני, בקרות אבטחה ונראות מלאה, אכיפת כללים אוטומטית על פני כל הצוותים, ניהול סודות מרכזי, ותצוגה אחודה של כל ה-APIs שנבנים בארגון. בקנה מידה גדול, כלים מפוזרים ותהליכים ידניים הופכים לסיכון ממשי, במיוחד לנוכח דרישות אבטחה ותאימות שהולכות וגדלות. ⠿

  • API Catalog     -  מקום מרכזי לראות ולנהל את כל ה-APIs, כולל אלה שבפיתוח ולא רק אלה שבפרודקשן.
  • API Governance -  הגדרת סטנדרטים וכללים ל-APIs ואכיפתם לאורך הפיתוח וה-CI/CD.
  • Private API Network -  קטלוג פנימי שמאפשר למפתחים למצוא ולצרוך APIs מאושרים של הארגון.
  • Advanced RBAC ובקרות ארגוניות - שליטה מדויקת על מי יכול לראות, לערוך, לפרסם ולגשת ל-APIs ולמידע.
  • Audit Logs, Reporting ו-API usage visibility - שקיפות מלאה על מי עשה מה, מתי, ואיך משתמשים ב-APIs.
  • Private Test and Flows Runners - הרצת בדיקות ו-Flows בתוך הסביבה הפרטית של הארגון, בלי לשלוח מידע לחוץ.
  • Insights - תמונה ברורה של פעילות ה-APIs, שימוש, תעבורה ודפוסי פעילות.
    AI Capabilities - יכולות מבוססות AI שמסייעות למפתחים ולצוותים בתהליכים שונים לאורך מחזור החיים של ה-API, כולל Design, Testing, Documentation, Governance ו-Development.
  • 800 קרדיטי AI משותפים למשתמש/חודש — קרדיטים חודשיים ליכולות ה-AI, משותפים בתוך הארגון.

כמה יכולות נוספות שיכולות להיות רלוונטיות, בהתאם לצרכי הלקוח:

Advanced Security Administration (ASA) - תוסף שמוסיף שכבת אבטחה ושליטה מתקדמת: Domain Capture, Account Discovery ו-Control, נראות ארגונית על Secret Scanner, אינטגרציה עם Azure Key Vault, AWS Secrets Manager ו-HashiCorp Vault, ו-BYOK.
  • מתי זה רלוונטי? כאשר רוצים לקבל שליטה מרכזית על Secrets, Accounts ו־Keys בארגון, לזהות חשיפה של Secrets ולחזק את שכבת האבטחה והשליטה סביב משתמשים וחשבונות ארגוניים.
  • דוגמה: עובד עוזב את החברה, משתמש אישי ממשיך להשתמש ב־Postman, או Secret של הארגון נמצא בקוד. צוות ה־Security רוצה לזהות ולשלוט במקרים האלה באופן מרכזי. כמו כן, כאשר רוצים לזהות Users במערכת ולמנוע או לאשר להם שימוש באמצעות Domain Capture.
Passport - תוסף אבטחה שמתמקד באיך מפתחים, אפליקציות ו-AI Agents מוצאים APIs בארגון ומקבלים אליהם גישה במקום לשאול ב-Slack מי יכול לשלוח API Key ולשמור אותו בקוד, מקבלים תהליך מסודר: למצוא, לבקש גישה, לקבל אישור, ולהשתמש בצורה מאובטחת, בלי לקבל את ה-Secret עצמו.
  • מתי זה רלוונטי? כאשר יש הרבה APIs והרבה צרכנים, וקשה לדעת מי רשאי לגשת למה, איך מקבלים הרשאה ואיפה נמצאים ה־API Keys וה־Secrets.
  • דוגמה: מפתח צריך גישה ל־Customer API. במקום לשלוח לו API Key ב־Slack ולשמור אותו ב־.env, הוא מוצא את ה־API, מבקש גישה, מקבל אישור וצורך אותו בצורה מבוקרת.
Fabric - שכבת בקרה מרכזית לעולם ה-AI בארגון. ככל שיותר צוותים עובדים עם מודלי LLM שונים, בונים AI Agents ומחברים AI למערכות פנימיות, Fabric נותן שכבה מרכזית לשלוט בתעבורה הזו, לאבטח אותה, להגדיר מה Agents יכולים לגשת אליו, לנהל Credentials, ולשלוט בעלויות ובצריכת Tokens.
  • מתי זה רלוונטי? כאשר הארגון מתחיל לעבוד עם מספר מודלי AI, Agents ו־MCP Servers ורוצה שכבת שליטה מרכזית על הגישה, המדיניות, האבטחה ועלויות ה־AI.
  • דוגמה: מספר צוותים משתמשים ב־OpenAI, Claude ו־Gemini ובונים Agents שמתחברים ל־APIs פנימיים. הארגון רוצה להגדיר איזה Agent יכול לגשת לאיזה API, באיזה Model מותר להשתמש וכמה Tokens נצרכים.
Fern  - פלטפורמה שהופכת API קיים ל-Developer Experience מלא
היא מייצרת באופן אוטומטי תיעוד, SDKs בשפות מרכזיות, CLI ו-MCP servers מתוך אותה הגדרת API אחת, כך שהם לא יוצאים מסנכרון אלה מאלה. פונה לצד ה-Consumption (איך צורכים את ה-API), לא לצד ה-Governance
  • מתי זה רלוונטי? כאשר יש APIs קיימים שצריך להנגיש בצורה פשוטה ומהירה למפתחים, שותפים או AI Agents, בלי שהצוות יצטרך לבנות ולתחזק Documentation, SDKs, CLI ו־MCP באופן ידני.
  • דוגמה: חברת ביטוח/כרטיסי אשראי חושפת API לשותפים עסקיים. במקום שכל שותף ילמד את ה־API ויבנה אינטגרציה מאפס, Fern מספק Documentation ו־SDKs מוכנים שמאפשרים להתחיל לעבוד מהר יותר.

מהירות מול איכות

המפתחים שלכם כבר משתמשים בכלים כמו Copilot או Cursor לכתוב קוד — וזה מעולה למהירות. הבעיה היא שקצב הבדיקות לא גדל באותו הקצב. אתם מקבלים יותר קוד, אבל לא יותר וידוא שהוא תקין. וזה בדיוק הפער שגורם לזינוק בתקלות שמגיעות לפרודקשן.

APIs שנבנו לבני אדם, לא לסוכני AI

יש נקודה שרוב החברות לא חושבות עליה בכלל: כשסוכן AI הוא זה שצורך את ה-API שלכם ולא מפתח אנושי, הוא צריך מפרט אחרת. סוכן AI לא 'מבין לפי הקשר' כמו מפתח — הוא צריך שיוצהר לו במפורש אילו פעולות אפשריות ומה המגבלות שלהן. אם ה-API שלכם לא כתוב כך, הסוכן פשוט ישתמש בו לא נכון — ואתם לא תדעו את זה עד שזה יקרה בפרודקשן.

Governance כבקבוק צוואר

וכשהכל רץ מהר יותר, Governance ואבטחה נהיים בקבוק הצוואר של הארגון. תיעוד ראיות לביקורת — audit evidence — הופך מתהליך שוטף לריצה ידנית פעם ברבעון. ואת זה אף אחד לא רוצה לעשות בלחץ.

ה-AI שבתוך Postman הוא לא כמו ChatGPT כללי.
אנחנו קוראים לו Agent Mode והוא בנוי במיוחד לעולם ה-API.
הוא רץ בתוך הסביבה שלכם ב-Postman, מכיר את כל הפרויקטים, הבדיקות וההתראות שכבר קיימים אצלכם, ולא רק עונה על שאלות אלא גם מבצע פעולות בפועל: כותב חוזים חדשים, מתקן בדיקות שנשברו, ומזהה מתי גרסה חדשה שוברת הבטחה שנתנו למישהו בעבר.
יש גם AI Engineer, שמתחבר למקום שבו שמור כל הקוד וההיסטוריה שלו (Git) ועושה עבודה עצמאית יותר/
לדוגמה, לעבור על כל ה-API-ים שלכם ולסמן אילו מהם כדאי להוציא משימוש כי הם ישנים או לא בשימוש, או לבדוק אוטומטית כל שינוי קוד חדש שמפתח מעלה למערכת, לפני שהוא מתקבל.
ואתם יכולים גם לבנות את כללי ה-Governance עצמם בעזרת AI — לכתוב אותם ב-Claude או ב-ChatGPT, ו-Postman הוא זה שבפועל אוכף אותם אוטומטית, על כל הפרויקטים, כל הזמן.

Fabric

Fabric הוא שכבת הבקרה המרכזית שלנו לעולם ה-AI בארגון.⠿

ככל שיותר צוותים מתחילים להשתמש במודלים שונים — OpenAI, Claude, Gemini — לבנות AI Agents, ולהתחבר לשרתי MCP ול-APIs פנימיים, כל צוות מתחיל לנהל בעצמו את החיבורים, ההרשאות וה-Credentials שלו.
Fabric מרכז את כל התעבורה הזו דרך נקודת שליטה אחת, כדי שהארגון יידע לאן בקשות ה-AI נשלחות, לאילו מודלים ו-APIs יש להן גישה, איך נשמרים הסודות, כמה זה עולה, ומה קרה בפועל- הכל תחתGovernance  אחיד. 

דוגמה
יש לכם צוות שעובד עם OpenAI, צוות אחר עם Claude, ו-Agent שמתחבר ל-MCP Server — וכולם צריכים גישה למערכות פנימיות. היום כל אחד מהם מחזיק Keys, הרשאות ולוגים משלו, ואין שכבה מרכזית שרואה את כל התעבורה.
עם Fabric, כל הבקשות עוברות דרך שכבת בקרה אחת: אם Agent מבקש GPT-5, Fabric יכול לאשר, לחסום, לנתב למודל אחר, לעבור ל-Claude אם יש תקלה, או לפצל את התעבורה בין כמה מודלים — הכל במקום אחד.
משפט סיכום
Fabric הוא שכבת הבקרה המרכזית שמחברת בין ה-AI, ה-Agents, שרתי MCP וה-APIs של הארגון — ונותנת שליטה על התעבורה, האבטחה, ההרשאות, העלויות וה-Audit, במקום שכל אחד מהם ינוהל בנפרד.

מה Fabric מאפשר לארגון⠿
  • נקודת שליטה מרכזית — לנהל ממקום אחד את התעבורה בין מודלים, Agents, שרתי MCP ו-APIs פנימיים.
  • Routing ו-Reliability — לנתב בקשות בין מודלים, לבצע Fallback אוטומטי כשמודל נופל, ולבחור את המודל המתאים לכל בקשה.
  • Security ו-Credential Management — ה-Agent לא צריך לראות או להחזיק את המפתחות בעצמו.
  • Agent Governance — לקבוע במדויק לאילו APIs, Tools או MCP Servers כל Agent מורשה לגשת.
  • שליטה בעלויות — לראות מי צורך כמה Tokens ובאיזו עלות, ולהגדיר תקציבים.
  • Audit מלא — לדעת מי הפעיל איזה Agent, על איזה מודל, לאיזה API ניגש, ואיזו Policy הופעלה.

Postman Passport

Passport הוא שכבת Governance מרכזית לגילוי, בקשת גישה וצריכה מאובטחת של APIs בארגון.⠿

ככל שיש יותר APIs ויותר אנשים, אפליקציות ו-AI Agents שצריכים להשתמש בהם, קשה לדעת מי משתמש במה, למי יש גישה, ולאן ה-API Keys וה-Secrets מתפזרים.מפתח מחפש API ב-Slack או בתיעוד, מבקש גישה ממישהו, וה-Key האמיתי מגיע לקבצי .env, לסקריפטים, ל-CI/CD ולעוד מקומות. וככל שיותר AI Agents מתחילים לגשת ל-APIs, האתגר הזה רק גדל.
אז במקום שמפתחים ו-AI Agents יקבלו את ה-API Key האמיתי ויפזרו אותו בקבצים, סקריפטים ו-CI/CD — הם מקבלים Reference של Passport.
ה-Credential האמיתי נשאר ב-Vault הקיים של הלקוח, ונפתר רק בזמן הקריאה בפועל ל-API. הארגון מקבל Visibility מלא על מי ביקש גישה, מי אישר, ואיך משתמשים ב-API — בלי לחשוף Secrets בשום שלב.

שאלות
  1. אם Key דלף היום ל-Repo או ל-Log — כמה זמן ייקח לגלות את זה?  אם התשובה לא ברורה, זה הכאב.
  2. מי מאשר גישה ל-API חדש היום, ואיך זה מתועד? אם התשובה היא "Slack" או "תלוי מי פנוי" — זה Signal חזק.
  3. איך מפתח היום מגלה ומבקש גישה ל-API פנימי?
  4. יש לכם דרך לדעת מי מחזיק אילו Keys כרגע?
  5. אתם משתמשים ב-HashiCorp / AWS Secrets Manager / 1Password?
  6. AI Agents צריכים גישה ל-APIs שלכם — איך זה מנוהל היום?
⠿
דוגמה :
צוות חדש בונה אפליקציה שצריכה API פנימי של לקוחות. המפתח צריך להבין מי הבעלים, למי לפנות, לקבל Key ולהכניס אותו למערכת. תכפילו את זה בעשרות APIs ומאות מפתחים — ובשלב מסוים הארגון כבר לא יודע מי מחזיק איזה Key, ולאיזה API יש לו גישה.
Passport נותן לארגון דרך מרכזית לגלות APIs, לנהל את הגישה אליהם ולאפשר שימוש מאובטח בהם — בלי לחשוף את ה-Credentials האמיתיים.⠿
איך Passport פותר את זה⠿
  • גילוי מרכזי — מפתחים ו-AI Agents מוצאים APIs מאושרים במקום אחד.
  • בקשת גישה מבוקרת — במקום לקבל את ה-Key האמיתי, מקבלים Reference של Passport.
  • Secretless Consumption — ה-Credential האמיתי נשאר ב-Vault הקיים של הלקוח, ונפתר רק בזמן הקריאה בפועל ל-API — בלי שהמשתמש או ה-Agent רואים או מעתיקים אותו.
  • Visibility מלא — מי ביקש גישה, מי אישר, ואיך בפועל משתמשים ב-API.
  • עובד עם הכלים הקיימים — משלים HashiCorp, AWS Secrets Manager, 1Password וכו', לא מחליף אותם.

Advanced Security Administration — ASA

ASA הוא ה-Add-on שרלוונטי לאבטחה בקנה מידה Enterprise ⠿

בגדול, זה נותן לצוות האבטחה שליטה מדויקת יותר על מי יכול להתחבר, מאיפה, ואיך שומרים על הסודות (secrets) שלהם. ברירת המחדל של Postman כבר מאובטחת, אבל ASA מוסיף שכבת בקרה נוספת שספציפית ל-Enterprise ולדרישות רגולציה כמו SOC 2, ISO או PCI. 
הוא גם כולל ניתוב אוטומטי של כניסות לפי דומיין (Domain Capture), לוח בקרה והתראות על ניסיונות חשיפה של סודות (Secret Scanner), חיבור לכספות חיצוניות שהם כבר עובדים איתן כמו Azure Key Vault, HashiCorp, AWS Secrets Manager, 1Password והצפנה במפתח שהם עצמם שולטים בו (BYOK).
ארגון שיש דרישת רגולציה להצפין את המידע שלו במפתח שהוא שולט בו לגמרי אז BYOK מאפשר את זה בלי לתת ל-Postman גישה למפתח ההצפנה.
ASA לא מחליף את האבטחה הבסיסית של Postman — הוא מוסיף עליה שכבת בקרה, ניראות ושליטה ברמת Enterprise, למי שצריך לעמוד בדרישות רגולציה מחמירות.

שאלות :
  1. כמה Personal Postman accounts אתם מעריכים שיש בארגון שלכם מתחת לרדאר?" — אם אין תשובה, זה בעצמו ה-Signal ?
  2. אם רגולטור ידרוש מחר הוכחה שמפתח ההצפנה שלכם אף פעם לא היה בידי Postman — יש לכם את זה מוכן?
  3. יש לכם היום ראייה מרכזית על כמה חשבונות Postman קיימים בארגון, כולל חשבונות פרטיים?
  4. יש דרישה רגולטורית ל-BYOK, או להחזיק את מפתח ההצפנה בעצמכם?
  5. היו לכם מקרים של Secrets שדלפו ל-Repos או ל-Logs?
⠿
מה כלול ב-ASA⠿
  • Domain Capture — ניתוב אוטומטי של כניסות לפי דומיין, כך שכל עובד נכנס לחשבון הארגוני הנכון בלי בלבול בין חשבונות אישיים לחשבון החברה.
  • Secret Scanner — לוח בקרה והתראות — לא רק סורק סודות בודד, אלא תמונת מצב ארגונית: כמה ניסיונות חשיפה קרו, איפה, ומי היה מעורב.
  • אינטגרציה עם כספות חיצוניות — Azure Key Vault, HashiCorp, AWS Secrets Manager, 1Password — כדי ש-Postman יעבוד עם התשתית שהלקוח כבר משתמש בה, לא יחליף אותה.
  • BYOK — הצפנה במפתח של הלקוח — הלקוח שולט לגמרי במפתח ההצפנה; Postman לא מקבל אליו גישה בשום שלב.

דוגמה: ארגון פיננסי שכפוף לרגולציה שמחייבת אותו להצפין את כל המידע הרגיש שלו במפתח שהוא עצמו שולט בו, ולא סומך על אף ספק חיצוני שמחזיק את המפתח. עם BYOK, הארגון שומר את מפתח ההצפנה בכספת שלו — ו-Postman פשוט לא יכול לגשת למידע בלי המפתח הזה, אפילו אם הוא ירצה. ⠿

Fern

FERN - פלטפורמה נפרדת שהופכת API קיים ל-Developer Experience מלא.⠿

Postman עוזר לך לבנות, לבדוק ולנהל API.
Fern לוקח את אותו API ועושה לו משהו אחר לגמרי — הוא הופך אותו לקל לצריכה, גם על ידי מפתחים וגם על ידי AI Agents.
ה-API של שלך יכול להיות מצוין מבחינה טכנית, אבל ברגע שמפתח חיצוני או פנימי צריך להשתמש בו, הוא שואל שאלות פשוטות: איפה ה-API? איך אני מתחבר? איזה SDK יש בשפה שלי? האם התיעוד בכלל מעודכן?
Fern יושב בדיוק בנקודה הזו — בצד ה-Consumption, כלומר איך צורכים את ה-API, לא ה-Governance. הוא לוקח את ה-API Specification ומייצרת סביבו אוטומטית תיעוד, SDKs בשפות מרכזיות, CLI ו-MCP servers מתוך אותה הגדרת API אחת, כך שהם לא יוצאים מסינכרון אלה מאלה.
אז Fern לוקח API קיים והופך אותו ל-Developer Experience מלא — לא רק מסמך שמתאר אותו

תיאור הבעיה
נניח שחברה בנתה API. מבחינת צוות הפיתוח — הוא קיים, הוא עובד, הכל בסדר. אבל מפתח חיצוני שמגיע מבחוץ שואל שאלות אחרות לגמרי: איפה ה-API, איך עושים Authentication, איזה Endpoint רלוונטי, איך מטפלים ב-Pagination, איזה SDK צריך, ואיפה בכלל הדוגמאות. וככל שה-API משתנה — וזה טוב, זה סימן שהעסק חי — נוצרת בעיה נוספת: השכבות API → Documentation → SDK → Examples יוצאות מסנכרון אחת מהשנייה. זה Drift, וזה הכאב המרכזי שרוב הארגונים חווים בלי לשים לו שם.
במוצר הזה אתה לא באמת קונה Documentation. אתה קונה דרך להפוך APIs למוצר שקל יותר לצרוך. ה-Documentation הוא בדרך כלל נקודת הכניסה, אבל Fern נותן סביב אותו API הרבה יותר מזה — וזה מה שהופך אותו לרחב בהרבה מכלי Documentation בלבד.

שאלות
  1. למה אתה מדבר איתי דווקא עכשיו? זו השאלה שמעלה את הכאב האמיתי.
    נתון גיבוי אם צריך: ב-Unleash, יותר מ-50% מתעבורת האתר מגיעה כיום מ-Agents, והתעבורה שלהם מ-Agents צמחה פי 12 מאז המעבר ל-Fern — "מוכנות ל-Agents" זו לא תיאוריה.
  2. יש לכם  Drift בין ה-API שלכם, ה-SDKs וה-Docs? כל כמה זמן?
    אם הלקוח יגיד שתחזוקה עצמית עולה לו רק כמה שעות Engineering — ה-Drift הוא התשובה שלך לזה.
    Drift הוא מצב שבו ה-API משתנה אבל התיעוד וה-SDKs לא מתעדכנים איתו, ובהדרגה הם מפסיקים לשקף את מה שה-API באמת עושה.
    שאלת המשך: מה קורה כשמשהו דחוף יותר נופל במקום? כמה זמן זה בפועל לוקח לתקן את הפער? מה נשבר לשותף בינתיים?
  3. אם מפתח רוצה להשתמש היום באחד ה-APIs שלכם, איך הוא מוצא את המידע שהוא צריך?
  4. כמה קל למפתח להגיע מהשלב שבו הוא מגלה את ה-API עד ל-API Call הראשון המוצלח?
  5. מי אחראי אצלכם על ה-Developer Experience של ה-APIs?
  6. אתם מתחזקים את ה-SDKs בעצמכם? אם כן — כמה מהעבודה הזו נעשית ידנית?
  7. האם אתם כבר חושבים על AI Agents שצורכים את ה-APIs שלכם? בונים MCP Servers היום?
  8. כמה זמן לוקח היום לשותף חדש לעבור מקבלת גישה ל-API עד שהאינטגרציה הראשונה שלו עובדת בפועל?

Free מול Enterprise Hosting — מה זה אומר בפועל⠿
ההבדל בפשטות תחשוב על זה כמו מנהל מרכזי ויחידות ביצוע. ב-Free, גם ה-Control Plane (ניהול והגדרות) וגם ה-Data Plane (עיבוד והעברת הנתונים בפועל) פועלים בענן של Postman — הדרך המהירה ביותר להגיע ל-Production. ב-Enterprise, ה-Control Plane נשאר בענן Postman, אבל הלקוח מריץ את רכיבי ה-Data Plane בענן הפרטי שלו — לשליטה במיקום הנתונים (Data Residency) ובידוד רשת. ⠿
  • מתי זה שווה את הכסף — אם הארגון כבר בענן Postman ואין לו מגבלת מיקום נתונים: כנראה שאין יתרון משמעותי. אם הוא חייב שהעיבוד יתבצע בענן שלו, דורש בידוד רשת, או כפוף לרגולציה/מדיניות אבטחה ספציפית: Enterprise עשוי להיות ממש רלוונטי.
  • נקודה חשובה לציין ללקוח — "Data Residency" לא אומר שכל הנתונים נשארים אצל הלקוח — ה-Control Plane עדיין בענן Postman. שווה לבדוק בכל מוצר ספציפי אילו נתונים עוברים בין הרכיבים, ומה בדיוק נשאר בצד הלקוח, לפני שמציגים את זה כסיבה לשדרג.

מה אתם מוסיפים מעבר ל-WAF / DDoS / Security tools?
לקוח: מה אתם מוסיפים מעבר ל-WAF* / DDoS* / Security tools? אני: אנחנו לא מתחרים ב-WAF, ב-DDoS או באימות שכבר יש לכם. אנחנו מוסיפים שכבת אבטחה שמתמקדת במחזור החיים של ה-API עצמו: Secret Scanner שמוצא סודות ומפתחות שדלפו בקוד ובקולקשנים, scorecards של אבטחה בתוך ה-API Catalog, וגישת shift-left* לבדיקות. לקוח: מה זה shift-left? אני: לבדוק אבטחה מוקדם, כבר בזמן הפיתוח, ולא רק בסוף. * WAF = חומת אש ליישומי ווב * DDoS = הגנה מפני הצפת תעבורה זדונית * shift-left = בדיקה מוקדמת, כבר בזמן הפיתוח לזכור: לא להתווכח עם ה-stack הקיים. לברר איפה יש gaps ב-lifecycle, Governance, secrets ו-testing.
האם אתם מחליפים את ה-API Gateway?
לקוח: האם אתם מחליפים את ה-API Gateway? אני: לא. ה-API Gateway ממשיך לנהל את התעבורה כמו היום. Postman מתחבר אליו, שואב ממנו מידע על ה-APIs, ומנהל את מחזור החיים של ה-API סביבו. לקוח: ואיך אתם יודעים מה קורה בסביבה? אני: אפשר גם להפעיל agent* שמאזין לפעילות בסביבה, בנוסף לחיבור ל-Gateway. * agent = עוזר AI שמבצע משימות לזכור: להפריד — Gateway מטפל בתעבורה; Postman מנהל את ה-API lifecycle סביבו.
