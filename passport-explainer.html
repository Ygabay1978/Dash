Passport

Passport היא שכבת Governance מרכזית לגילוי, בקשת גישה, וצריכה מאובטחת של APIs בארגון — בלי לחשוף Secrets.

⠿

תחשוב על זה כך: ככל שיש יותר APIs, ויותר אנשים, אפליקציות ו-AI Agents שצריכים להשתמש בהם, נהיה קשה יותר לדעת מי משתמש במה, למי יש גישה, ואיפה בפועל שוכבים ה-API Keys וה-Secrets. מפתח מחפש API ב-Slack או בתיעוד, מבקש גישה ממישהו, וה-Key האמיתי מסתיים בקבצי .env, בסקריפטים, ב-CI/CD ובעוד מקומות. Passport נותן שכבת Governance מרכזית לגילוי, בקשת גישה, וצריכה מאובטחת של APIs — בלי לחשוף את ה-Secrets בפועל.

במשפט אחד: Passport נותן לארגון דרך מרכזית לגלות APIs, לנהל גישה אליהם, ולצרוך אותם בבטחה — בלי לחשוף אף פעם את ה-Credentials האמיתיים.

⠿
מכאן אתה עובר לבעיה

צוות חדש בונה אפליקציה שצריכה API פנימי של לקוחות. המפתח צריך לגלות מי בעל ה-API, למי לפנות, לקבל מפתח, ולהוסיף אותו לאפליקציה. הכפל את זה בעשרות APIs ומאות מפתחים — ובשלב מסוים, הארגון פשוט לא יודע למי יש איזה מפתח או גישה לאיזה API. וככל שיותר AI Agents נכנסים לתמונה ומבקשים גישה ל-APIs, האתגר הזה רק גדל.

שאלות Discovery — כולל שתי השאלות המרכזיות
⠿
תרחיש ראשון: חברת ביטוח
חברת ביטוח עם סוכנים חיצוניים ו-AI Agents

סוכני ביטוח חיצוניים, שותפים, וגם AI Agents פנימיים צריכים גישה ל-APIs של פוליסות ותביעות. היום, הגישה מנוהלת ידנית — טיקט, אישור, מפתח שנשלח באימייל או ב-Slack.

הבעיה: כשסוכן/שותף מפסיק לעבוד, לא בטוח שמישהו זוכר לבטל את הגישה שלו. Passport נותן בקשת גישה מסודרת, אישור, ותוקף מוגבל — ומאפשר לבטל גישה במקום אחד ברגע שצריך.

למי לפנות: Head of API/Platform (ה-Lead), CISO/Compliance (Audit Trail).

שאלת Discovery לסגירת התרחיש"אם סוכן חוץ מפסיק לעבוד איתכם היום — כמה זמן לוקח לדעת בוודאות שהגישה שלו ל-API בוטלה?"
⠿
תרחיש שני: חברת אשראי
חברת אשראי עם צוותי Fraud/Risk וגישה ל-Payment APIs

צוותי Fraud, Risk ושותפים חיצוניים צריכים גישה ל-Payment APIs רגישים. יש חשש אמיתי (ולרוב דרישת PCI) שמפתחות API יזלגו ל-Repos, ל-Logs או לקבצים מקומיים.

Passport מקטין את הצורך להפיץ את ה-Key האמיתי בכלל — במקום זאת, ה-Reference עובר, וה-Credential עצמו נשאר ב-Vault ומתפענח רק ברגע הקריאה. זה בדיוק העוגן שה-Compliance Team מחפש.

למי לפנות: Head of API Platform (ה-Lead), Risk/Compliance (Sponsor שקט אבל חשוב).

⠿
תרחיש שלישי: בנק
בנק עם עשרות צוותי פיתוח

בבנק עם 40 צוותי פיתוח, למשל, צריך למנוע מצוות תשלומים לגעת ב-Workspace של HR — בלי שמישהו יצטרך לנהל את זה ידנית כל יום. וככל שיותר AI Agents פנימיים נכנסים לתמונה, השאלה "מי בכלל יכול לגשת למה" נהיית קריטית יותר.

Passport נותן לארגון שכבת Governance ארגונית אחת: Discovery מרכזי, בקשת גישה מסודרת, וצריכה בלי לחשוף Secrets — עם Audit Trail מלא שרגולטור יכול לבדוק.

למי לפנות: Head of API Architecture / Platform (ה-Lead), Compliance/Risk (שותף קריטי).

  • AI Agents צריכים גישה ל-APIs שלכם — איך זה מנוהל היום?

התנגדויות נפוצות

"יש לנו כבר Vault (HashiCorp/AWS/1Password)"
AEמצוין — Passport לא מחליף את ה-Vault, הוא מוסיף שכבת Access Governance מעליו: מי מבקש, מי מאשר, ואיך זה נצרך.
"זה עוד שכבת אישורים שתאט אותנו"
AEהמפתח עצמו לא משתנה בזמן ריצה — מה שמשתנה הוא השקיפות: מי בקש, מי אישר, ומה נצרך. זה לא מוסיף Latency לקריאת ה-API.
"אנחנו סומכים על המפתחים שלנו"
AEזה לא עניין של אמון — זה עניין של מה קורה כשמישהו עוזב, כשמפתח מגיע ל-Repo ציבורי בטעות, או כשרגולטור שואל מי בדיוק ניגש למה בשנה האחרונה.

תמחור

התמחור תלוי במספר ה-APIs וה-Users/Agents שמנוהלים ב-Passport, ובגודל הארגון. אין מספר גנרי אחד להגיד בשיחה ראשונה.

אם המחיר עולה בשיחה הראשונה"זה תלוי בהיקף — כמה APIs, כמה משתמשים ו-Agents דורשים גישה מבוקרת. נצלול לזה בהערכה עם Specialist."
