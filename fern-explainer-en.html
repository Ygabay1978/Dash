Fern

Postman helps you build a good API. Fern helps make it actually get used — by developers and by AI Agents.

⠿

Think about it this way, and open the conversation right at this point: Postman helps you build, test, and manage an API. Fern takes that same API and does something completely different with it — it makes it easy to consume, both by developers and by AI Agents.

The customer's API can be technically excellent, but the moment an external or internal developer needs to use it, they ask simple questions: where is the API? How do I connect? What SDK exists in my language? Is the documentation even up to date? Fern sits exactly at this point — on the Consumption side, not the Governance side. It takes the API Specification and automatically builds around it documentation, SDKs, a command-line tool, and MCP servers for AI Agents.

From here you move to the problem

Say a company built an API. From the dev team's point of view — it exists, it works, all good. But an external developer coming from outside asks completely different questions: where is the API, how does Authentication work, which Endpoint is relevant, how is Pagination handled, which SDK do I need, and where are the examples at all. And as the API changes — which is good, it's a sign the business is alive — another problem appears: the layers API → Documentation → SDK → Examples drift out of sync with each other. That's Drift, and it's the central pain most organizations experience without having a name for it.

The customer isn't really buying Documentation. They're buying a way to turn APIs into a product that's easier to consume. Documentation is usually the entry point, but Fern gives much more than that around the same API — and that's what makes it far broader than just a documentation tool.

First scenario you can lay out: a bank
A large retail bank

It has APIs for accounts, payments, cards, and open banking — and needs external Fintech partners and internal teams to integrate with them. The situation: dozens of APIs across different departments, documentation that's inconsistent between them, and SDKs maintained by hand for the languages partners actually use.

The business problem: a new Fintech partner wants to launch a feature using the bank's Payments API. They need to read the docs, figure out authentication, build against it, and debug integration issues — often taking weeks. Fern can deliver: API Specification → Documentation + SDKs + Examples — cutting that integration time down significantly.

And because it's a bank, Fern's ability to run Self-Hosted (running the Documentation and SDK generation inside the bank's own infrastructure) can matter a lot in the conversation — satisfying data residency and security requirements, worth raising it early.

How to close the pitch

The important distinction to remember, if a question comes up about Postman itself: Governance / Management / Discovery → Postman. Consumption / Developer Experience → Fern. Fern doesn't replace the API Catalog — it sits downstream, the broader layer around the APIs: business context, Guides, examples, Troubleshooting. If the customer is a Postman customer, Postman stays their first point of contact.

Discovery Questions

  • Why are you talking to me right now?
    This is the question that surfaces the real pain.
    Backup data if you need it: at Unleash, over 50% of website traffic now comes from Agents, and their agent traffic grew 12x since moving to Fern, "agent-readiness" isn't a theory.
  • Is there drift between your API, your SDKs and your docs? How often?
    If the customer will say self-maintenance costs them just a few engineering hours — Drift is your answer to that.
  • Follow-up question: what happens when something more urgent comes up instead? How long does it actually take to fix the gap? What breaks for a partner in the meantime?
  • If a developer wants to use one of your APIs today, how do they find the information they need?
  • How easy is it for a developer to go from discovering the API to their first successful API call?
  • Who owns the Developer Experience of your APIs?
  • Do you maintain your SDKs yourselves? If so — how much of that work is manual?
  • Are you already thinking about AI Agents consuming your APIs? Building MCP Servers today?
  • How long does it take today for a new partner to go from getting access to the API to their first integration actually working?

Common Objections

"We already have Documentation"
AEGreat. The question isn't just whether documentation exists, but how easy it is to maintain and keep in sync with the API and SDKs. How do you handle Drift today between the API, the Docs, and the SDK?
"We build this ourselves"
AESure, you can build this yourselves. The question is how much Engineering effort it costs you today, and how much it costs to maintain over time. What happens when there's an API change? How many places need to be updated?
"We already have Mintlify / ReadMe / GitBook"
AESo the question is whether you're looking for just Documentation, or a broader API Consumption layer. Do you also generate SDKs? CLI? MCP? How do you keep them in sync with the API?
"We have Postman's API Catalog"
AEGreat — they actually complement each other. Catalog helps you understand which APIs exist, and Fern helps a developer understand how to use each API.
"We're a secure organization, we can't send our API Specs to the cloud"
AEThat's exactly one of the reasons Self-Hosted is relevant — Fern lets you run Docs and SDK Generation on your own infrastructure, including On-Prem or Private Cloud.
"We don't need AI Agents"
AEThat's fine — Fern doesn't have to be an AI project. The core value is Documentation, SDKs, and Developer Experience. The AI/MCP piece is an additional usage layer that can become relevant later.

Competition

Mintlify — the biggest competitor. Two winning arguments

1. Fern is a full product line, not a single Feature. Documentation, SDKs, CLI, and MCP servers in one platform, where the Docs automatically link to everything else Fern generates. Mintlify is documentation only.

2. Fern is backed by Postman. A $5.5 billion company, kept as an independent product line with its own Roadmap.

Pricing

Per product, and value-based — by API complexity, scale (surface area for an external API, number of Microservices for internal), and company size/revenue.

Documentation: from $4,000 (Enterprise floor) up to $800,000 for a large, technologically spread-out organization. SDKs: similar floor, up to $500,000 per language. Discount: up to 50% off list price.
