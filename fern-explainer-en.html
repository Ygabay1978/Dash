Fern

Postman helps you build a good API. Fern helps make it actually get consumed — by developers, and by AI Agents.

⠿

Think of it this way, and open the conversation exactly at this point: Postman helps you build, test and manage an API. Fern takes that same API and does something completely different with it — it makes it easy to consume, both for developers and for AI Agents.

A customer's API can be technically excellent, but the moment an external or internal developer needs to use it, they ask simple questions: where's the API? How do I connect? Which SDK is there in my language? Is the documentation even up to date? Fern sits exactly at that point — on the Consumption side, not the Governance side. It takes the API Specification and automatically builds around it: documentation, SDKs, a command-line tool, and MCP servers for AI Agents.

Documentation
Docs-as-code — lives in Git next to the code, auto-updates on every API change via CI/CD
SDKs
9 languages — the only vendor with production Swift. A deterministic, consistent way to connect to the API, so no developer (or agent) has to invent Auth and Pagination on their own
CLI
Command-line access to the API — an organized function tree, for agents too. There's also fern diff — a command that shows exactly where the API, the SDK and the Docs have drifted out of sync
MCP Servers
A full MCP server for the API itself, not just for the docs

Worth saying: the documentation is served as Markdown on the server side (not the client side), so Claude Code, Codex and Cursor can read it and work with it directly. The SDK in particular matters for agents: an agent building against an API with no SDK makes inconsistent decisions (Auth, Pagination), which raises token spend and lengthens development time.

The one sentence worth knowing by heart: Fern takes an existing API and turns it into a full Developer Experience — not just a document describing it.

⠿
From here, move to the problem

Say a company built an API. From the engineering team's point of view — it exists, it works, all is fine. But an external developer coming from outside asks completely different questions: where's the API, how do I do Authentication, which Endpoint is relevant, how do I handle Pagination, which SDK do I need, and where are the examples at all. And the more the API changes — which is good, it's a sign the business is alive — another problem appears: the layers API → Documentation → SDK → Examples drift out of sync with each other. That's Drift, and it's the core pain most organizations feel without ever naming it.

The customer isn't really buying Documentation. They're buying a way to turn APIs into a product that's easier to consume. Documentation is usually the entry point, but Fern gives much more than that around the same API — which is what makes it far broader than a documentation tool alone.

First scenario you can lay out: an insurance company
A large insurance company

It has APIs for customers, policies, claims, quotes and agents — and it lets partners and insurance agencies connect to them. The typical state: hundreds of APIs, documentation scattered in different places, SDKs built by hand, and every API change requires updating several places.

The business problem shows up the moment a new agency wants to connect. They need to go through documentation → understand Authentication → understand Endpoints → build an integration → troubleshoot. Fern can give: API Specification → Documentation + SDKs + Examples — and the partner gets a much more organized way to start working.

And because this is an insurance company, Fern's ability to run Self-Hosted (running the Documentation and SDK generation inside the customer's own infrastructure, including On-Prem or Private Cloud) can be a meaningful part of the conversation — worth raising early, not waiting for them to ask. This is mainly relevant for regulated industries — banking, insurance, payments, defense (companies like Bloomberg, Anduril and Intuit run Self-Hosted). Point worth remembering: in practice, many of these customers move to Hosted later on, once they've seen for themselves the Compliance and Performance of the managed environment — so you can start Self-Hosted with no hesitation, and let it evolve.

Who to target at an insurance company like this: Head of Open Banking/API or Head of API Product (the Lead), Head of Developer Portal (second role). CISO/Compliance enters the picture once a regulatory Audit (DORA/PSD3) comes up — that's exactly the moment Self-Hosted moves from a theoretical question to a requirement.

Who to target at a credit company like this: Head of API Product/Platform (the Lead), VP Engineering (second role). A good signal to check beforehand: search GitHub for "unofficial [company name] SDK" — if "unofficial" community-built SDKs exist, it means they don't have a good official SDK, and that's exactly the gap Fern closes.

Discovery Questions

Key question #1 — then be quiet "Why are you talking to me right now?" This is the question that surfaces the real pain — ask it, and leave the silence alone. Don't fill it. Backup data if you need it: at Unleash, over 50% of website traffic now comes from Agents, and their agent traffic grew 12x since moving to Fern — "agent-readiness" isn't a theory.
Key question #2 — this is the money one "Is there drift between your API, your SDKs and your docs? How often?" The customer will say self-maintenance costs them just a few engineering hours — Drift is your answer to that. Follow-up: what happens when something more urgent comes up instead? How long does it actually take to fix the gap? What breaks for a partner in the meantime?
  • If a developer wants to use one of your APIs today, how do they find the information they need?
  • How easy is it for a developer to go from discovering the API to their first successful API call?
  • Who owns the Developer Experience of your APIs?
  • Do you maintain your SDKs yourselves? If so — how much of that work is manual?
  • Are you already thinking about AI Agents consuming your APIs? Building MCP Servers today?
  • How long does it take today for a new partner to go from getting access to the API to their first integration actually working?

Who Fern fits — and who it doesn't

Titles to look for: Developer Experience / DevRel (Head of DevRel, Director of Developer Platforms) · API Product Owners (PM, Engineering Manager, Director of Engineering) · Platform Engineering (mainly for the internal use case). All of them roll up to VP Engineering — an exec-level conversation works well too.
The real sweet spot: not a company that never thought about this — a company that's already trying to solve it themselves and falling behind. Twilio, for example: 10 people maintaining SDKs, 10 maintaining Docs, two Major Versions behind their own OpenAPI — and they still signed a six-figure deal. That's the tell: heavy manual effort + a lagging result.
Internal APIs have real pain too (Platform Engineering): in a typical internal case, engineers waste time on Slack asking colleagues how an internal API works, and Agents can't pull that information reliably themselves. Non-technical teams (Sales, Analysts) also get stuck without understanding the API's Intent. Fern solves both sides — faster development, less cross-team friction. Worth remembering: AEO (exposure to external AI) is only relevant to public Docs — internal Docs don't need models to "learn" from them, but still benefit from MCP with Auth Passthrough, from llms.txt, and from internal AI search.

Common objections

"We already have Documentation"
AEGreat. The question isn't just whether docs exist, but how easy it is to maintain them and keep them in sync with the API and SDKs. How do you handle Drift between the API, Docs and SDK today?
"We're building this ourselves"
AEOf course you can build this yourselves. The question is how much engineering effort that costs you today, and how much it costs to maintain over time. What happens when the API changes? How many places need to be updated?
"We already use Mintlify / ReadMe / GitBook"
AESo the question is whether you're looking for Documentation only, or a broader API Consumption layer. Are you also generating SDKs? CLI? MCP? How do you keep them in sync with the API?
"We have Postman's API Catalog"
AEGreat — they actually complement each other. Catalog helps you understand which APIs exist, and Fern helps a developer understand how to use each API.
"We're a security-conscious org, we can't move our API specs to the cloud"
AEThat's exactly why Self-Hosted is relevant — Fern lets you run Docs and SDK Generation on your own infrastructure, including On-Prem or Private Cloud. You can start that way, no pressure — in practice, a lot of regulated customers move to Hosted later on, once they see the Compliance and Performance of the managed environment.
"We don't need AI Agents"
AEThat's fine — Fern doesn't have to be an AI project. The core value is Documentation, SDKs and Developer Experience. AI/MCP is an additional usage layer that can become relevant later.

Competition

Mintlify — the biggest competitor. Agent-friendly, but missing a lot

Mintlify is genuinely agent-friendly, and builds agent-readiness at a similar pace — but it has no: Enterprise scale, Multi-repo, RBAC, Self-Hosting, and no SDKs / CLIs / MCPs at all. It's docs only.

The winning argument: Fern is a full product line — Documentation, SDKs, CLI and MCP servers on one platform, where the Docs automatically link to everything else Fern generates. And also: Fern is backed by Postman, a $5.5B company, with more capital and a faster roadmap pace.

Pricing

Per product, value-based — driven by API complexity, scale (surface area for an external API, number of microservices for internal), and company size/revenue.

Documentation: from $4,000 (Enterprise floor) up to $800,000 for a large, technologically sprawling organization. SDKs: a similar floor, up to $500,000 per language, priced separately from Documentation. An SDK for an internal API is priced lower than one for an external API. Discount: up to 50% off list price.

Reference point: a Series B/C company with 200-500 endpoints, in TypeScript + Python + Java, comes out around $30,000 (about $10,000 per language). NVIDIA-scale deals (150-300 products, complex parsing) go much higher. Always use the pricing calculator for ranges, and bring in a specialist before a formal quote.
